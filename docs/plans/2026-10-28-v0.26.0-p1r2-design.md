# v0.26.0 P1 and R2 design: four false `equivalent` verdicts of the behavior diff

Status: design, 2026-10-28, at `805b3bbe`. Read-only study. No source changed.
Authority: the [v0.26.0 plan](2026-10-27-v0.26.0-plan.md), Decision 5(a) (P1 in this release) and Decision 11(a) (R2 is R0 items 3a, 4a, and 4d, fixed with P1 under one `path_analyzer_version` rise; item 4b is disclosed, not fixed).

Labels. "Observed" means I ran a command or read the code. "Inferred" means I reasoned from observed facts and ran no check. "Predicted" marks a value that the failing test must confirm.

## 1. Summary

All four items reproduce on `main` (section 2). Each one is a path record that holds less than the program does, so the diff compares two equal records for two different programs.

- P1: `packages/zts/src/path_generator.zig#extractExprStatus` records 200 for every status that is not an integer literal in an options object. The gap is wider than the plan states (section 3).
- 3a: the path walk does not enter a user function that the handler calls by name. The gap is wider than "a named closure" (section 3).
- 4a: an arm of a returned `match` adds no constraint, so a changed pattern leaves the path record unchanged.
- 4d: a `match` bound to a name and returned later is one leaf with status 200.

The recommended fix has one data-model change: a behavior status is `known(u16)` or `unknown`, and the diff never treats `unknown` as equal to any status, except under the existing `same_program` exemption. The other three fixes reuse existing machinery: the `if` constraint extraction (4a), the block-continuation fork (4d), and the inline-callback recorder (3a).

Measured blast radius over the 263 tracked `.ts` files (section 10): 10 files have a return whose status falls back to 200 today, 7 files call a same-file helper that holds a module call, 1 file (`examples/routing/match-handler.ts`) gains match constraints, and 0 files have a bound `match` with response arms. The union is 17 files. All 143 files that self-compare today are `equivalent`. After the fix, 2 of them are predicted to self-compare `breaking`, by the documented `same_program` rule.

## 4. Shared data model

### 4.1 The status type

Add to `packages/zts/src/contract_types.zig`:

```zig
pub const ResponseStatus = union(enum) {
    known: u16,
    unknown,
};
```

Use it for `BehaviorPath.response_status`, `GeneratedTest.expected_status`, `BehaviorPathChange.status`, `CallSiteEntry.failure_status`, and `fault_coverage.Diagnostic.status`. Observed with Zig 0.17: `a != b` on a `union(enum)` is a compile error ("operator != not allowed for type"). So the compiler lists every comparison site. Do not use `std.meta.eql` on this type in a verdict, because it treats `unknown` as equal to `unknown`. Tests may use `std.testing.expectEqual`.

Decision 17 chooses this type over `?u16` and over a sentinel.

### 4.2 The only verdict comparison

Add one function to `packages/zts/src/contract_diff.zig`:

```zig
fn statusesEqual(a: ResponseStatus, b: ResponseStatus, same_program: bool) bool {
    return switch (a) {
        .known => |x| switch (b) {
            .known => |y| x == y,
            .unknown => false,
        },
        .unknown => same_program and b == .unknown,
    };
}
```

`unknown` never equals a known status. `unknown` equals `unknown` only when the caller proved `same_program` (identical IR identity and only built-in imports, `packages/zts/src/contract_diff.zig#diffContractsFromSources`). This is the rule that `#ioSignaturesEqual` already applies to a `?` argument. Decision 18 chooses it.

`diffBehaviors` and `takeMatchingPath` do not receive `DiffOptions` today. Thread `options` from `#diffContractsWithOptions` into `#diffBehaviors` and `#takeMatchingPath`. Then `#takeMatchingPath` with `require_status_equal` and `#canonicalPathsEqual` call `statusesEqual`. An `unknown` old path then fails the exact-status pass, matches in the second pass, and counts as `response_changed`, which `BehaviorDiff.hasBreaking` reads as breaking.

Consequence, inferred from the code: strict `#diffContracts` of a contract with an `unknown` status against itself is `breaking`. `packages/runtime/src/live_reload.zig#diffAgainstCurrent` uses the strict form when it has no old source, so such a hot swap reads `breaking`. This is the same cost that a `?` argument has today.

## 5. P1: the status of a returned value

### Root cause

Observed in `packages/zts/src/path_generator.zig#extractExprStatus`: a returned value that is not a `call` or `method_call` returns 200; a call whose callee fails `#isResponseHelper` returns 200; a helper call whose second argument does not yield a status from `#extractStatusFromOptions` returns 200. Observed in `#extractStatusFromOptions`: it reads only an `object_literal`, skips any property that is not `object_property` (a spread), skips a `status` value that is not `lit_int`, and drops a `lit_int` outside 100 to 599.

### Fix

The status of a returned value, in order. Decision 19 chooses these rules.

1. A call of `Response.json`, `text`, `html`, or `rawJson` with fewer than two arguments: `known(200)`. Add `rawJson` to `#isResponseHelper`. Observed: the runtime treats `rawJson` like `json` (`packages/zts/src/http.zig#responseRawJson`).
2. The same call with an object literal second argument. Read the properties in order. A `status` property whose value is a `lit_int` in 100 to 599 gives `known(value)`. A `lit_int` outside that range gives `known(500)`, which mirrors `#normalizeStatus`. Any other `status` value gives `unknown`. A spread anywhere in the object gives `unknown`, unless a literal `status` property follows the last spread. No `status` and no spread gives `known(200)`.
3. The same call with any other second argument (an identifier, a call): `unknown`.
4. `Response.redirect(url)`: `known(302)`. `Response.redirect(url, n)` with `n` a `lit_int` in 100 to 599: `known(n)`; outside the range: `known(500)`. Any other second argument: `unknown`.
5. Any other returned value: `unknown`. This covers an identifier, a user helper call, `hole()`, a route dispatch, and a ternary.

Do not resolve a status through a binding (`const o = { status: 404 }`, `const r = Response.json(...)`). Inferred risk: the profile admits property assignment (`req.params = found.params` in `examples/routing/router.ts`), so a later `o.status = 500` would make the resolved value wrong. The tracked corpus has 0 such return sites (section 10), so the rule costs nothing measured.

A route dispatch (`return found.handler(req)`) becomes `unknown`. Observed: this costs no precision, because a `routerMatch` handler is already `breaking` on any edit that is not a no-op. `router_a.ts` against `router_c.ts` (one JSON field changed in a route body) gives `breaking` with `preserved=2 response_changed=0` today, because the `routerMatch(routes, req)` call carries `?` arguments.

## 6. 4a: a changed arm pattern with the same status

### Root cause

Observed in `packages/zts/src/path_generator.zig#walkReturnedValue`: each arm saves and restores the constraints and walks its body, and adds no constraint. Its doc comment states this residual. So the arms "GET", "POST", and default of `t5a_a.ts` give three paths that differ only by status.

### Fix

An arm adds the constraints that the equivalent `if` chain adds. Decision 20 chooses this scope.

- Discriminant `d` and an arm pattern that is a string literal `P`: the arm's constraint is `#extractLiteralComparison(d, P)`, the function that `if (d === P)` uses. It yields `req_method` when `d` is `req.method` or the `const` that `#findHandlerBindings` bound to it, `req_url` for `req.url` or `req.path`, and the stub constraints for a module-call result. It yields nothing for any other `d`, the same as `if`.
- Arm `k` also receives the negation (`#negateConstraint`) of each earlier arm's constraint, as an `else if` chain does. `default` receives the negations of every earlier arm.
- A record pattern on the request binding (`match (req) { when { method: "GET", path: "/health" }: ... }`) yields one constraint per field named `method`, `url`, or `path` whose pattern is a string literal. Later arms walk once for each way the earlier conjunction is false, as `#falseCases` does for `&&`: `[¬a]`, then `[a, ¬b]`. Build these lists directly; there is no IR node for the conjunction.
- After the push, `#solveConstraints` drops an arm that conflicts with an enclosing request constraint, as for `if`.

`#dupePathCondition` records `req_method` and `req_url` in the contract and drops the negative forms, the same as for `if`. No new `PathCondition.Kind` is needed.

Predicted effects. `t5a_a` against `t5a_b`: the "POST" path and the "PUT" path no longer share a key, so `preserved == 2`, `removed == 1`, `added == 1`, verdict `breaking`. `disc_a` against `disc_b`: `req_method` against `req_url` keys, `breaking`. `t5a_a` against `order_b`: the contract keys are equal, `equivalent`. `mx_a` against `mx_b` (header value): no constraint, `equivalent`, the same as `ifx_a` against `ifx_b`. `zts gen-tests t5a_a.ts`: the second test sends `POST` and the third sends `PUT`, the first method in `request_method_candidates` that the negations do not exclude. `examples/routing/match-handler.ts`: 4 paths become 6. Observed: the `if` chain with the same three conditions (`ifchain.ts`) gives `Execution paths: 6 (exhaustive)` today.

## 7. 4d: a `match` bound to a name and returned later

### Root cause

Observed. `packages/zts/src/path_generator.zig#walkPaths` `.var_decl` stores the initializer in `var_inits` and calls `#trackModuleCall` on the whole `match`, which records every arm's module calls in one flat sequence. `return r` then reaches `#walkReturnedValue`, which forks only when the returned node itself is a `match_expr`. An identifier is one leaf, and `#extractExprStatus` gives 200.

### Fix

Fork at the declaration, not at the return. In `#walkBlockFrom`, when the statement is a `var_decl` whose initializer is a `match_expr` and the match qualifies (Decision 21), do this for each arm, in source order:

1. Record the discriminant's module calls once, before the fork, as `#walkReturnedValue` does.
2. Push the arm constraints of section 6.
3. Record the arm body's module calls under the declared binding key.
4. Bind the declared name to the arm body for this path only, in a per-path map that `#extractExprStatus` reads for an identifier.
5. Walk the rest of the block (`#walkBlockFrom(block, i + 1)`), then restore the constraints, the I/O sequence, and the binding.

Do not run the flat `#trackModuleCall` for a forked declaration. If the fork ran at `return r` instead, each arm's calls would be recorded twice, once flat at the declaration and once per arm.

`#extractExprStatus` resolves an identifier through that per-path map only when two conditions hold. First, the declaration is `const` (`Node.VarDecl.kind`). Second, no assignment in the walked function has the name as the root of its target, so a later `r.status = 500` cannot change the response. Otherwise the status is `unknown`. Observed by grep: none of the six tracked files that bind a `match` assigns to the bound name or a member of it. The guard is cheap to compute once per root.

A match qualifies when at least one arm body is a `Response` helper call (section 5 rule 1 to 4) or holds a module call. A match whose arms are all pure values does not fork. Its pattern and value changes stay the pure-computation blindness of Decision 4(a). The value used as a status (`matchs_200`) is `unknown` by section 5, so that pair becomes `breaking` through P1.

Observed census: 6 tracked files bind a `match` (all under `tests/corpus`), and every arm body is a pure value with 0 module calls. No tracked file returns a bound match by name. So the recommended rule moves 0 tracked contracts.

## 8. 3a: a module call inside a user function called by name

### Root cause

Observed in `packages/zts/src/path_generator.zig#trackModuleCallUnder`: the `.function_decl, .function_expr, .arrow_function` arm returns, and a call is recorded only when `#getCalleeMeta` resolves the callee to a module export. A call to a user function records nothing, and `#walkPaths` does not enter a function either. Only a function written inline as a call argument is entered (`#trackInlineFunctionBody`). The doc comment of `#trackModuleCallUnder` states this residual.

### Fix

At a call whose callee is an identifier that resolves to a user function in the same file, record the module calls of that function's body at the call site. Decision 22 chooses the scope. Resolution, in order:

1. A module-level function or module-level `const` function value: `EffectFacts.functions` (`packages/zts/src/effect_inference.zig#EffectFacts`) by `binding_key`. Observed: `#collectFunctionsIn` records both, keyed by `packBindingKey(scope_id, slot)`, the same key the generator uses.
2. A local `const` closure: `var_inits` holds a `function_expr` or `arrow_function`.
3. A nested `function` declaration: collect them in a pre-pass over the root function body, keyed the same way.

The recording rules:

- Evaluation order: the arguments first, then the callee body (`#trackModuleCallUnder(body, null, false)`), then nothing for the user call itself.
- Multiplicity: the body inherits `#currentMultiplicity` at the call site, so a call under a loop carries the loop bound.
- Binding: the inner calls take no binding key. A test on the outer result (`x === undefined`) gives no stub constraint for an inner call, so fault coverage does not claim it covered.
- An identifier argument that resolves to a user function (`xs.map(g)`) is recorded like an inline callback, once, after the other arguments.
- Recursion: keep a stack of bodies under expansion; a body already on the stack is not expanded again. `#detectRecursionReach` already marks the path set as not exhaustive for recursion.
- Unchanged: an imported function, a method on an object, a function value read from a structure. `imp_a` against `imp_b` stays `equivalent`. This is the cross-file form of the gap, and it belongs to the G1 area (Decision 4(a)). Disclose it in `docs/proofs-and-receipts.md`.

Side effects, inferred from `#scanUnseenFailableCalls`: an inner call becomes a recorded stub, so it leaves the unseen list. Without a constraint it has no failure path, so the site moves from "unseen" to "uncovered". `fault_covered` stays refused, and the proof-trace text and `fault_unseen_cause` change. `max_io_depth` and the cost envelope grow. `cost_bounded` can move from true to false when a helper with a module call runs under an unbounded loop; that is a correct loss of an over-claim. `fault_covered` must not move from false to true; if it does, the unit stops (section 11).

## 12. Risks

- Path growth. The 4d fork multiplies paths by the arm count of each qualifying bound match, and 4a multiplies by the false cases of record arms. `MAX_PATHS` truncates, and truncation makes the coverage `truncated`, which refuses path properties. Measured growth in the corpus is 4 to 6 paths in one file.
- `same_program` is strict. A handler with a local import and an `unknown` status is `breaking` against itself. Two tracked files reach this, and both are codegen fixtures.
- Helper expansion cost. Each call to a helper re-walks its body on every path. A deep helper chain under many paths is slower. Measure `zig build test-precompile` time before and after; this needs to be measured, not estimated.
- `var_inits` holds `let` initializers too. The existing constraint code reads them without a `const` check (inferred, not probed). This unit adds no new reader of `var_inits` without the `const` and no-assignment guard.
- The record-pattern lowering in 4a builds constraint lists by hand. A wrong false-case enumeration drops a path. The `match-handler.ts` count of 6, equal to the `if` chain, is the check.
