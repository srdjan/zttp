The ZTS language.

ZTS is a constrained application language with TypeScript-shaped source, compiler-visible authority, typed failure, and compiler-visible proof claims. The model-minimal cutover is complete: one core profile, one optional TSX frontend, and no JavaScript compatibility path.

01

The language in one pass

ZTS reduces authoring choices where those choices hide control, authority, or proof state. It keeps familiar syntax when the compiler can give it one stable meaning.

01 Name the data structural defines transparent shapes. nominal creates scalar identities.
02 Show the branch Conditions are boolean. Tagged unions use exhaustive match. There is no general truthiness.
03 Type the failure Result<T, E> carries recoverable failure. undefined means absence. null is data.
04 Expose authority Named zttp:* modules and a closed ambient intrinsic set feed explicit capability and proof facts.
05 Ask the compiler Grammar, examples, idioms, repairs, and verifiers are machine-readable. Canonical source is shared by agents and humans.
source .ts or .tsx Typed source with explicit file identity
frontend typed core TSX lowers first; types produce evidence
checks types, flow, effects Failures stay located and structured
execution bytecode and VM Governed calls form the effect boundary
evidence contract and receipt Artifacts bind profile and source identity

ZTS is a constrained language, not TypeScript compatibility. TypeScript lexical habits make the source readable, but the live grammar and checker define the language. Files ending in .js or .jsx are rejected.

02

Source and type system

The type layer is expressive enough for application data and small enough to erase without becoming runtime evidence.

types.ts 
nominal OrderId = string;

structural Command =
  | { kind: "echo"; text: string }
  | { kind: "ping" };

structural Tree<T> = {
  readonly value: T;
  readonly children: readonly Tree<T>[];
};

function describe(command: Command): string {
  return match (command) {
    when { kind: "echo", text }: text
    when { kind: "ping" }: "pong"
  };
}
Primitives
boolean, number, string, null, undefined, unknown, never, and Bytes.
Composition
Records, arrays, tuples, functions, literal types, unions, intersections, and constrained generics.
Identity
nominal creates a distinct string, number, or boolean identity with an unchanged runtime value.
Recursion
Recursive aliases are accepted when every cycle passes through a record, tuple, array, or Dict.
Utilities
Readonly, Pick, Omit, Partial, and Required.
Need ZTS form Boundary
Application shape structural User = { ... }; Transparent and structurally assignable.
Scalar identity nominal UserId = string; The constructor adds identity, not validation.
Public behavior Named function with parameter and return types Fixed arity. Reusable or exported arrow helpers and function expressions are refused; direct arrow callbacks stay inside typed, finite APIs.
Module boundary Named import, named export, or import type No default export, wildcard import, side-effect import, or dynamic import.
Text construction String(value) and [a, b].join("") No template interpolation or string-valued addition.
Record update Explicit fields, with at most one leading spread No shorthand, computed keys, methods, getters, or setters.

Types never manufacture evidence. Type predicates are checked before they narrow. Proof and Effects annotations are compared with facts inferred from function bodies. Assertions such as as and satisfies are outside the profile.

03

Control and failure

Branches, iteration, failure, and absence use different forms. The checker never has to guess which channel a value belongs to.

Control stays visible

Use if for statement branches, a pure ternary for two values, and match for one scrutinee with multiple cases. assert is reserved for programmer invariants.

Iteration stays finite

for...of iterates a finite snapshot. Pure collection transforms use typed array or Dict operations. Recursion can run, while totality and cost claims remain separate proof questions.

failure.ts · separate absence from recoverable failure 
structural Result<T, E> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly error: E };

structural DivideError = { kind: "division-by-zero" };

function divide(a: number, b: number): Result<number, DivideError> {
  if (b === 0) {
    return { ok: false, error: { kind: "division-by-zero" } };
  }
  return { ok: true, value: a / b };
}

function describe(result: Result<number, DivideError>): string {
  return match (result) {
    when { ok: true, value }:
      ["ratio ", String(value)].join("")
    when { ok: false }:
      "undefined ratio"
  };
}
Situation Write Reason
Optional value value !== undefined or value ?? fallback No truthiness. The branch states whether absence or content matters.
JSON null Name null in the type and compare or match it null is data, not an alias for an omitted value.
Recoverable error Result<T, E> The error is a typed return path, never an exception channel.
Invariant breach assert condition; Expected application guards use if plus an explicit return.
Boolean composition a && b, a || b, !a Operands and result are boolean. Operators never return an operand value.
04

Effects stay visible. Proofs are return types.

Authority enters through visible module calls and a closed set of compiler-known ambient intrinsics. A function can publish the capabilities it may use and the properties the compiler must discharge.

Effects<T, R>

A capability ceiling. The inferred effect row must be a subset of R. Exported effectful helpers declare it; internal helpers rely on inference.

Proof<T, P>

A property obligation. The compiler checks the body and reachable calls, then reports the evidence or a located counterexample for each requested property.

handler.ts · checked against the live compiler zero diagnostics 
import { sha256 } from "zttp:crypto";

structural Guarded<T> = Proof<T,
  | "deterministic"
  | "state_isolated"
  | "no_secret_leakage"
>;

function handler(_req: Request): Guarded<
  Effects<Response, "crypto">
> {
  return Response.json({ digest: sha256("zttp") });
}

Published verifier properties

pure read_only stateless deterministic has_egress state_isolated retry_safe idempotent fault_covered results_safe optional_safe input_validated no_secret_leakage no_credential_leakage pii_contained injection_safe canonical post_only cost_bounded

The annotation is an obligation, not a promise the compiler trusts. A body that reaches a capability outside its Effects ceiling or fails a named Proof property does not check.

05

TSX is a frontend, not the core

A .tsx file selects the separately identified zts-tsx-1 frontend. It lowers UI syntax to ordinary calls before the core parser runs.

authored .tsx source Elements, fragments, props, and children
strip type evidence Source locations remain mapped
lower zts-tsx-1 Versioned frontend with its own grammar hash
target h(tag, props, ...children) Ordinary core calls only
parse zts-model-1 The core contains no JSX node kind
page.tsx
function Card(props: { title: string }): JSX.Element {
  return <section class="card">
    <h2>{props.title}</h2>
  </section>;
}
lowered core
function Card(props) {
  return h(
    "section",
    { class: "card" },
    h("h2", null, props.title),
  );
}

The frontend is intentionally small. It has no component lifecycle, hooks, class components, ambient state, or hidden scheduling. A .ts file containing JSX and every .jsx file are refused.

06

The application surface

The built-in module catalog exposes data operations, runtime authority, and structured orchestration. The registry assigns every export a capability set and an effect class.

none 64

No intrinsic export effect

read 9

Runtime reads without mutation

write 39

I/O, mutation, or scheduled callbacks

These are intrinsic export classifications. A higher-order call joins its callback's effects into the inferred row, so a Result combinator can still be effectful.

Data and boundary tools Values, parsing, validation, routing, and text +
zttp:bytes zttp:collections zttp:decode zttp:http zttp:json zttp:result zttp:router zttp:text zttp:time zttp:url zttp:validate
Explicit authority Environment, identity, storage, network, and observability +

Structured orchestration Bounded concurrency, resources, queues, and replay +

Imports are authority declarations. The compiler also tracks the closed ambient varying reads such as Date.now() and Math.random(). It derives least-privilege runtime policy from the reachable graph, while each compiler FunctionBinding records an export's signature, effect, capabilities, replay classification, failure severity, provenance labels, and algebraic laws.

07

What stays outside

The omissions are part of the language design. Each removed family either duplicates an admitted operation or hides state, control, authority, or type evidence from the compiler.

Hidden control

Exceptions, async/await, Promises, generators, detached tasks, and ambient scheduling.

Hidden state

Classes, inheritance, new, dynamic this, prototypes, and mutable module-global application state.

Open execution

while, C-style loops, user-defined iterators, dynamic imports, eval, reflection, and proxies.

Type escape hatches

any, assertions, satisfies, overloads, index signatures, conditional types, and mapped types.

Implicit coercion

Loose equality, truthiness, unary plus, string addition, mutation shorthand, assignment expressions, and automatic semicolon insertion.

Dynamic shapes

Computed record keys, deletion, object methods, getters, setters, regex construction, namespaces, and decorators.

type / interface structural One transparent data-contract declaration.
switch match Tagged narrowing and checked exhaustiveness without fallthrough.
throw / catch Result<T, E> One visible, typed return channel.
while / for (;;) for...of / finite fold The iteration domain remains explicit.
template interpolation String + join Conversion and concatenation are separate operations.
computed object key Dict<K, V> Fixed records keep their shape; dynamic keys use a typed collection.
08

The compiler is part of the language

The profile publishes its grammar, examples, idioms, modules, diagnostics, validators, and verifier vocabulary through one versioned agent protocol.

zts agent --stdin-json 10 schema-v2 operations cover discovery, checks, bound repairs, normalization, and property verification.
zts check handler.ts --json Returns located diagnostics and proof traces for the checked handler.
zts canonicalize handler.ts --json Returns canonical source and bound candidates without writing the workspace; source writes go through the host's aggregate change-set proof.
zts normalize handler.ts --check Runs the fixed-point normalizer, bounded at 64 iterations, and checks byte-stable output.
zts spec-check --json Checks semantic tables, lowering structure, differential cases, and SMT obligations.

Current semantic disposition

IR nodes 69 / 69
Opcodes 127 / 127

All reachable entries are classified. 12 IR nodes and 7 opcodes have direct specified semantics; 1 opcode path is translation-validated. The remaining 57 nodes and 119 opcodes are explicit trusted-boundary entries with narrow reasons.

Classification is wider than mechanized semantics. The independent assurance certificate and verifier remain proposed. Current proof grades are useful compiler evidence, but they do not become an independently checked end-to-end certificate by being signed or hashed.

Start writing

Begin with a named handler, check it against the live profile, then inspect the compiler's structured answer before adding authority.

terminal 
# See the current compiler-owned language contract
zts agent --stdin-json < request-meta.json

# Check, canonicalize, and verify one handler
zts check src/handler.ts --json
zts canonicalize src/handler.ts --json --simulate
zts normalize src/handler.ts --check
zts verify-paths src/handler.ts --json
