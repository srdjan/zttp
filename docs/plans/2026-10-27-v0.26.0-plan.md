### A5: per-export capabilities (S11)

Observed in code: `packages/zts/src/module_binding_adapter.zig#adaptFunctionBinding` passes the module-level capability set to `wrapToNativeFn`. `readsVaryingSource` in `packages/zts/src/flow_interp.zig` already reads the per-export field. Not run.

Step 0, done by the lead on 2026-10-27: every per-export `required_capabilities` in `packages/modules/src` is a subset of its module set, and `validateBindings` already requires that. No export declares a capability outside its module set, so A5 is not a bypass of a declared capability. It closes a different gap: the analyzer trusts the per-export set (for example, `readsVaryingSource` in `packages/zts/src/flow_interp.zig` reads it for `deterministic`), and the runtime enforces only the wider module set. Native code that uses a capability its export does not declare therefore breaks a proof with no refusal. Fix: `adaptFunctionBinding` passes `binding.required_capabilities orelse` the module set to `wrapToNativeFn`. Test: an extension binding whose export declares no capability and whose native function calls a capability helper for a capability in the module set; the call is refused after the fix and allowed before it. If an existing builtin export fails because its native code uses an undeclared capability, the unit stops and reports it: that is a proof defect, and a declaration change is model-visible. Gates: `test-modules`, `test-module-scope-panic`, `test-capability-audit`, `test-zruntime`, `test-examples`, `test`.

Execution: commit 00004c73; test `adapted export enforces its declared capabilities at call time` failed before the fix (expected false, found true); gates test-modules, test-module-scope-panic, test-capability-audit, test-zruntime, test-examples, test-module-boundary, test-proof-swallow, test, check-spine, module-spec-render --check exit 0.

### A6: an authorized request is not resent (S15)

Observed in code: `namesCredential` in `packages/modules/src/net/fetch.zig` refuses a retry only when the init names a key `credential`, which `FetchOptions` cannot carry. A request with an `authorization` header is therefore resent up to `maxRetries` times. Not run. Correction to the validation round: `hasCredentialOption` in `packages/runtime/src/runtime_http.zig` is not a retry guard. It refuses the retired `credential` option on every fetch, so A6 does not change it.

Fix: `fetchWithRetry` refuses with `CredentialRefused` when the init headers carry `authorization`, `proxy-authorization`, or `cookie`, compared case-insensitively. Deviation from revision 2, decided by the lead on 2026-10-27: a non-idempotent method without a credential is still retried. The original design (M4 T6, section 5, Q2) accepts a resent write and refuses only a credential, and refusing every POST would break existing handlers beyond finding S15. Test: a local listener that answers 503 counts requests; a request with an `authorization` header through `fetchWithRetry` is refused before any request is sent, and the same request without the header is retried. Gates: `test-modules`, `test-server`, `test-zruntime`, `test-examples`, `test`.

Revision by Decision 9 (a), 2026-10-27: a credential header refuses the retry only when the method is not GET, HEAD, or OPTIONS. A missing method counts as GET, and a method the guard cannot read counts as unsafe. The retired `credential` option stays refused for every method. Before the revision, the test `fetchWithRetry retries a GET with an authorization header` failed (expected 503, found 599). The changelog lists the refusal of a credentialed write as a breaking change.

Execution: commit 670ae5f1; test "fetchWithRetry refuses an authorization header before any request is sent" failed before the fix (expected 599, found 503; the mixed-case test failed the same way and the cookie and proxy-authorization test found "none" for "CredentialRefused"); gates fmt-check of fetch.zig and zruntime_tests.zig, test-modules, test-server, test-zruntime, test-examples, test-flow-census, test, build, module-spec-render --check, check-spine exit 0.

### P2: `capability_bounded` claimed for every contract

Observed: `packages/runtime/src/build_command.zig#dischargedProperties` and `packages/runtime/src/proof_ratchet.zig#certify` set `capability_bounded = handler_contract.capabilities != null`, which holds for every built contract. The kernel defines the property as "the inferred capability set sits inside the declared ceiling" (`packages/proof-checker/src/proof_system.zig#Property`). The certificate discloses the property at `tested`, so the kernel does not accept it as proved. The claim is still more than any check established.

P2 is research: find where a declared ceiling exists, if anywhere; what the production floor and the deploy path do when the producer reports the property false; and the smallest true producer rule. The result goes to the owner as a decision before any change.

Result, 2026-10-27 (`p2/RESULT.md` in the session scratchpad; the lead confirmed the floor and the producer in code): the only declared ceiling is an `Effects<Response, "...">` return type. When a handler declares one, `dischargeCapabilityBudget` in `packages/zts/src/contract_builder.zig` checks the inferred effect row against it, and an overrun is an error. With no `Effects<...>`, nothing is checked. `contract.capabilities` is the union of the imported modules' capabilities, never null. The production floor (`packages/proof-checker/src/policy.zig`) requires `capability_bounded` at `tested`, so a producer value of false refuses build, deploy, and startup. Two example files declare `Effects<...>`. The fix waits for Decision 10.

### G1: a changed helper reaches the handlers that read it

Observed in the validation round:

- A pull request that changes only a pure helper with a `Proof<...>` capsule gives exit 0. `analyzeHandler` returns null for a file that exposes no routes, and `run` records it as `no_contract`.
- A helper that fails its own root analysis gives exit 2. Examples: ZTS061 on a raw primitive in an exported signature, or ZTS611 with ZTS500 on a record without a capsule. `examples/handler/utils.ts` fails with three ZTS061. Most helper-only pull requests fail closed today, for the wrong reason.
- Even when the importing handler is compared, a helper's returned value is invisible. The contract diff compares behavior paths, status, and effects, not pure computation. This is the same blindness as for an edit inside a handler file. When the helper gains `fetch`, the importing handler loses `retry_safe`, which is critical, so that case gives exit 1 once the handler is compared.

Design: the gate runs the recording scan for every changed candidate, handler or not. It lists the tracked `.ts` files on each side, and drops the files with no handler using a parse-only filter (`CheckResult.has_handler`). It runs CHECK on each remaining handler with a recording `ImportReader`. On the working tree, the recording reader wraps `file_io.readFile`, as `RevisionReader.read` does for a ref. It normalizes each recorded path with `repoRelativePath`. A handler whose reads on either side include a changed file joins the compared set as a modified handler. The changed-file list uses `--no-renames`, so a renamed helper is listed under both paths. A changed helper that no handler reads is skipped with reason `unreferenced_helper`. A helper's own analysis no longer stops the gate; a compared handler that fails analysis still gives exit 2. Decision 4 sets the verdict rule.

The CHECK traversals read every transitive relative import, with two exceptions: an import behind a helper that fails its type check, and an import past `max_import_depth` (8). Each exception gives exit 2, with a test. A deleted helper that a head handler still imports also gets a test.

Step 0 has two tests: an effect change in a pure helper with a capsule gives exit 1, and a helper that fails its own analysis no longer gives exit 2 when its importer analyzes. Step 0 also measures the gate's run time on this repository before and after the change. A slowdown beyond what a CI step tolerates goes to the owner. Docs: the roadmap limitation, and a roadmap sentence on `utils.ts`. Gates: as G2.

### C1: certificate assurance design study

Observed: the consumer re-derives only `response_total`. `results_checked`, `no_secret_leakage`, and `capability_bounded` enter at `tested`. `docs/verification.md:574` names `results_checked` as the next family. `capability_policy.zig` decodes the residual runtime allowlists, not a capability ceiling. The executable graph commits the capability matrix only as a digest. The proof IR lowers `capability_call` only for guarded calls with an unresolved resource.

Per family, the kernel would need:

- `results_checked`: Result-binding dataflow with `.ok` narrowing across branches.
- `capability_bounded`: every capability-reaching call lowered with its catalog row, the ceiling in the certificate, and a set-union rule. Its rule is the simplest of the three, but P2 must fix the producer first.
- `no_secret_leakage`: full label propagation with declassifiers and `env.public`. This is the largest.

Decision 8 selects the family. C1 writes the consumer rule, the producer evidence, the mutant that the checker must reject, and the cost. C2 needs a separate owner approval of that design.
