Patterns from Antfly's Zig code

Antfly's Zig tree contains useful examples of explicit ownership, bounded work, and checks that detect empty tests or stale generated source. This page selects patterns that have a clear source and a practical use in another Zig project.

Code evidence

Nine patterns with clear boundaries

These are selective examples from a large tree. They are useful because they make a failure mode visible in code or in a test.

01 / Build graph

Give each build unit an owner

The root build imports build modules for selected package and library units. Its create() function can return a typed Artifacts value. Other build code can use those artifacts instead of defining a second graph for them.

This makes those build steps easier to trace. It gives the owner a place to define generated files, tests, and link inputs.

build.zig:15-55build.zig:89-102sql/build_support.zig:16-32

Use in zttp. Keep public step names in the root build. Move a build unit to its owner when that unit has enough inputs and outputs to need a clear boundary.

Limit. More build modules add navigation cost. A small graph can stay in one file.

02 / Generated source

Make drift checks read-only

The SQL grammar build declares the grammar input and generated output. It provides one step to update checked-in source and another step to compare bytes without changing that source. The check also compiles the checked-in generated file.

This makes a drift result easy to trust: a check reports a mismatch, while a separate command performs the repair.

sql/build_support.zig:36-64build.zig:249-261

Use in zttp. Apply this shape when a Zig tool writes a tracked table, schema, or documentation artifact. Make the source inputs and check step explicit.

Limit. Antfly has other generators with different tool dependencies. The SQL path is the example here.

03 / Compile time invariant

Check that a closed set is complete

Antfly keeps runtime archive link order in a separate array because link order differs from enum order. A comptime check rejects a duplicate and requires every enum value exactly once.

The array can change order without losing coverage. A new enum value causes a compile error until the build order covers it.

runtime.zig:30-57

Use in zttp. Use this check for a closed registry or policy table whose order has meaning. Test both completeness and uniqueness.

Limit. This does not help when the set is open at runtime. The cited file has a separate license; reuse the idea, not its code.

04 / Error model

Keep expected diagnostics as values

The SQL lexer returns either tokens or a bounded diagnostic value. Allocation failure remains a Zig error. The implementation states who owns the returned memory and uses errdefer to clean partial work.

Tests cover public tokenization behavior and each allocation failure point. This checks the error path as well as the normal path.

lexer.zig:70-99lexer.zig:589-615

Use in zttp. Keep an expected source error as structured data when a caller needs a location or reason. Test cleanup at allocation failure points.

Limit. A simpler lexer entry point reduces the diagnostic to one error tag. Callers that need detail must choose the detailed API.

05 / Owned state

Publish only complete state

The in-memory object store builds the body, ETag, and metadata under cleanup guards. It checks cancellation during the copy. It replaces the old value or inserts a new value only after the new value is complete.

The cited tests check allocation cleanup while a read result is built. They also check that an already canceled write creates no object. The useful rule in the write code is to make the publication point easy to identify.

memory.zig:102-149memory.zig:492-519

Use in zttp. Use this shape for state shared across requests: prepare the replacement in owned memory, then make one visible change.

Limit. Antfly uses a fixed copy chunk in this path. A suitable size for another workload needs to be measured.

06 / Capability boundary

Pass resources and state limits

The object store client carries an allocator, an opaque context, and a table of operations. Optional operations show which capabilities a provider has. File upload takes an explicit std.Io value. Its fallback refuses an input above a stated size instead of reading without a bound.

The cancellation token is borrowed and states its lifetime rule. The interface keeps those resource choices visible to its caller.

client.zig:22-48client.zig:73-95types.zig:18-55

Use in zttp. When a runtime interface supports several backends, show optional capabilities and resource limits in the API. Test each fallback as a separate behavior.

Limit. Antfly uses anyerror in its vtable. That broad error set gives callers less error detail.

07 / Test runner

Fail a test run that selects nothing

Antfly's test runner counts matches for each requested filter. It exits with failure when a filter matches no declared test or when the full selection has no runnable tests. For each selected test, it creates fresh test memory and I/O state, tears both down, and records a memory leak as a failure.

This prevents a green result from a misspelled filter. It also links a leak to the test that caused it.

test_runner.zig:82-115test_runner.zig:126-184test_runner.zig:229-245

Use in zttp. Require a nonempty match before a filtered test result counts as evidence. This directly addresses the empty-filter risk described in the repository rules.

Limit. Antfly has an explicit flag that permits an empty filter. A custom runner also adds maintenance work. The cited file has a separate license; reuse the rule, not its code.

08 / Deterministic tests

Save the inputs needed to replay a fault

Antfly's VOPR simulation checks a scenario's required declarations at compile time. Its choice source selects from enabled, typed transitions. A trace records the scenario version, source revision, target, build mode, budgets, fixture hashes, feature flags, and the selected transitions.

The runner checks the trace's scenario name and version. It also normalizes observations before it hashes them. That makes a failed simulation easier to replay and compare.

scenario.zig:13-27choice.zig:51-103trace.zig:12-61runner.zig:571-607

Use in zttp. If a concurrency or fault test uses a seed, save the choices and versioned context with a failed run. Check all context fields needed for a valid replay.

Limit. Antfly records more context than its compatibility check compares. A simulation checks its model, so separate tests must check that the model represents production behavior. VOPR files have a separate license.

09 / Performance evidence

Require enough evidence before a speed verdict

Antfly's database benchmark summary has minimum counts for measured work. It checks those counts with correctness, memory, and latency limits. It can also compare results with a stored baseline. A failed check returns an error.

This keeps a fast result from passing if the run did too little work or produced wrong output.

db_query_summary.zig:255-302db_query_summary.zig:689-722db_query_summary.zig:1409-1447db_query_summary.zig:1492-1516

Use in zttp. Put a minimum workload and a correctness check beside each performance limit. Record the benchmark configuration with the result.

Limit. Antfly's guardrails are optional and default limits can be open. A baseline field that is absent can become zero during parsing. Validate the baseline schema before relying on a comparison.

Practical use

Where to start in zttp

Apply a pattern only where a real change needs it. These checks are small enough to attach to the next relevant unit of work.

For a test gate

Check that it selected at least one test. Fail on an empty filter before the run can count as evidence.

For mutable runtime state

Build the replacement before a shared reference changes. Test failure and cancellation at the point before publication.

For generated artifacts

Give regeneration and drift checks separate steps. Make the drift check read-only and compile the tracked result when it is source code.
