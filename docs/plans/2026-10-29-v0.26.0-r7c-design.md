# v0.26.0 R7c design: the pi tools read the production session

Status: draft 2, after Fable validation. Decision 46 is decided: (a).

## Goal

`pi_repair_plan`, `pi_goal_check`, and `zts_expert_narrow` take their verifier and flow diagnostics from the analysis that `zts check` runs. Decision 43 requires this before the W re-record: the ZTS309 phase reads the type checker's record, and `pi_repair_plan` builds `HandlerVerifier` with no type checker, so a ZTS309 refusal gets no diagnostic and no repair plan in that tool.

## Observed state at `257a8482`

Each tool parses the source itself and runs bare checkers on the one file:

| Tool | Bare analysis | Production analysis |
|---|---|---|
| `packages/pi/src/tools/pi_repair_plan.zig` | `HandlerVerifier.init(..., null, null)` and `FlowChecker` | `pi_goal_check.unprovenGoals` for `ok` |
| `packages/pi/src/tools/pi_goal_check.zig` | `FlowChecker` | `unprovenGoals` for `ok` |
| `packages/pi/src/tools/zts_expert_narrow.zig` | `FlowChecker` | none |

`unprovenGoals` runs `zts_cli.precompile.runCheckOnlyFromSourceWithOptions`, so `pi_repair_plan` analyzes the file twice. The production run (`packages/tools/src/precompile_check_run.zig`) owns a `ModuleAnalysisSession` local to the call. After `runVerifier` and `runFlow` it holds the typed `checked.verifierDiagnostics()` and `checked.flowDiagnostics()`, then drops them when it returns. `CheckResult` keeps only counts and JSON diagnostics, which carry no node and no verifier shape, so `repair_plan.fromVerifierDiagnostic` cannot run on them.

The R7c census (reset worklog, R7 section) over 182 `tests/corpus` cases: the tools refuse 39 before analysis (17 admission, 22 parse). Of the 143 cases that the tools analyze, 46 equal production and 97 differ. In 9 cases the tools report 10 bare-only diagnostics where production stops at an earlier stage. In 12 cases `pi_repair_plan` differs from the two flow-only tools.

## Mechanism

Add an observer to `CheckOptions`, which `packages/tools/src/precompile_check_run.zig` defines (line 39) and `precompile.zig` re-exports:

```zig
pub const CheckedObserver = struct {
    context: *anyopaque,
    on_checked: *const fn (context: *anyopaque, checked: CheckedView) error{OutOfMemory}!void,
};

pub const CheckedView = struct {
    ir_view: zts.IrView,
    atoms: *zts.AtomTable,
    handler_fn: zts.parser.NodeIndex,
    verifier_diagnostics: []const zts.VerifierDiagnostic,
    flow_diagnostics: []const zts.FlowDiagnostic,
};
```

`runCheckOnlyFromSourceWithPathAllocator` calls `on_checked` once, directly after `runVerifier` and `runFlow`, while the session is alive. The view borrows everything; a tool copies what it keeps. The callback may fail only with `OutOfMemory`. The check turns every other error into a `compiler_io_failure` diagnostic at 1:1 (lines 310 to 319), so a wider error set would read as a false analyzer failure. A tool keeps any other failure in its own context and reports it after the check returns. The check's own output does not change, so `zts check` stays byte-identical.

`zts.FlowDiagnostic` is a new curated alias in `packages/zts/src/root.zig` for `flow_checker.Diagnostic`, beside `VerifierDiagnostic` (line 732). Without it, the view in `packages/tools` would reach the internal `flow_checker` module, and `scripts/module-boundary.allow` has no `tools flow_checker` row. The other view types are curated already. `zig build test-module-boundary` confirms no new row.

The observer positions come from `getLoc` and are raw. Production remaps its JSON diagnostics with `normalize_positions = true` (lines 321 to 323). The shared helper applies the same remap to every position that it takes from the view, so tool positions and `zts check` positions agree.

Each tool then runs one production check with an observer and builds its envelope inside `on_checked`:

- `pi_repair_plan`: diagnostics and plans from the verifier list, witnesses from the flow list, `ok` from the `CheckResult` as `unprovenGoals` decides it today. The second analysis goes.
- `pi_goal_check`: witnesses from the flow list, `ok` and `unproven` as today. `unprovenGoals` stays public for `pi_repair_plan` callers that need only the verdict, or folds into the shared helper (implementer's choice, named in the commit).
- `zts_expert_narrow`: witnesses from the flow list.

One shared helper in `packages/pi/src/tools/common.zig` (or a new `production_check.zig`) owns the workspace path, the project discovery (`discoverProjectPaths`, policy, SQL schema), and the call, so the three tools do not each repeat what `unprovenGoals` does now. The helper passes `json_mode = true`, because the check collects verifier, flow, bool, type, and import diagnostics only in JSON mode. It passes the workspace-relative path, as `packages/pi/src/tools/common.zig#checkJsonOutcome` does, because the `file` field reaches tool output and the test "a repair plan reads the same from two different workspaces" in `pi_repair_plan.zig` asserts the same output under both roots. `env_public` then comes from the policy, as in production, in place of `common.discoverEnvPublic`.

The callers outside the tools need no change. `autoloop.zig`, `pi_goal_candidate.zig` (lines 111 and 439), and `evaluateSource` already send in-memory source through `unprovenGoals` to the production check, with the cwd as the workspace root. The `pi_goal_check` envelope keeps its `ok` and `witnesses` keys, which `parseGoalCheckResult` in `autoloop.zig` reads.

## Decisions

- 46, a check that ends without running the verifier and the flow pass. There are two ways. First, production stops at a parse, type, strict, or import error. Second, the file passes those stages and has no handler: the call point is inside `if (handler_fn) |hf|`, and the check returns `has_handler = false` with no diagnostic. (a) For a stop at an error, the tool returns `ok: false` with the production JSON diagnostics as its diagnostics, and no witnesses or plans. For a file with no handler, the tool keeps its present error, "no handler function found in file". Recommended: the tool then says what `zts check` says, and a verdict never stands on an analysis that checked nothing. (b) Fall back to the bare checkers for those cases. This keeps two analyzer routes, which Decision 2 set out to remove. (c) Return a tool error with no diagnostics in both cases.

A former Decision 47 (refuse `.js` in the tools) is struck. Both routes classify sources with `classifyPath` (`packages/zts/src/source_frontend.zig`): both refuse `.js` and both accept a `<name>` virtual source. The only difference is the error text against a ZTS052 diagnostic, and 46(a) gives the tool the ZTS052 diagnostic.

5. A file with no handler returns "no handler function found in file" from each tool.

## Measurement

The census becomes a committed test: `test "R7c census: tool diagnostics equal production over tests/corpus"` in the pi package, next to the shared helper. It iterates the `tests/corpus` cases, which the census exemption in AGENTS.md permits. For each case it runs `pi_repair_plan` and the production check, and it compares the diagnostics by code and position. It asserts a floor of 182 cases found, and it fails on any difference. It reports the count of refusals before analysis (39 at the census). The pi tool tests run in `test-expert-app`. That step stays red until W, so the acceptance for that step is: the only failing tests are the two known W tests, "codegen baseline replays at the committed first-attempt green rate" and "search preserves frozen response bytes". Any difference in the census stops the unit and goes to the owner.
