### G1: a changed helper reaches the handlers that read it

Observed in the validation round:

- A pull request that changes only a pure helper with a `Proof<...>` capsule gives exit 0. `analyzeHandler` returns null for a file that exposes no routes, and `run` records it as `no_contract`.
- A helper that fails its own root analysis gives exit 2. Examples: ZTS061 on a raw primitive in an exported signature, or ZTS611 with ZTS500 on a record without a capsule. `examples/handler/utils.ts` fails with three ZTS061. Most helper-only pull requests fail closed today, for the wrong reason.
- Even when the importing handler is compared, a helper's returned value is invisible. The contract diff compares behavior paths, status, and effects, not pure computation. This is the same blindness as for an edit inside a handler file. When the helper gains `fetch`, the importing handler loses `retry_safe`, which is critical, so that case gives exit 1 once the handler is compared.

Design: the gate runs the recording scan for every changed candidate, handler or not. It lists the tracked `.ts` files on each side, and drops the files with no handler using a parse-only filter (`CheckResult.has_handler`). It runs CHECK on each remaining handler with a recording `ImportReader`. On the working tree, the recording reader wraps `file_io.readFile`, as `RevisionReader.read` does for a ref. It normalizes each recorded path with `repoRelativePath`. A handler whose reads on either side include a changed file joins the compared set as a modified handler. The changed-file list uses `--no-renames`, so a renamed helper is listed under both paths. A changed helper that no handler reads is skipped with reason `unreferenced_helper`. A helper's own analysis no longer stops the gate; a compared handler that fails analysis still gives exit 2. Decision 4 sets the verdict rule.

The CHECK traversals read every transitive relative import, with two exceptions: an import behind a helper that fails its type check, and an import past `max_import_depth` (8). Each exception gives exit 2, with a test. A deleted helper that a head handler still imports also gets a test.

Step 0 has two tests: an effect change in a pure helper with a capsule gives exit 1, and a helper that fails its own analysis no longer gives exit 2 when its importer analyzes. Step 0 also measures the gate's run time on this repository before and after the change. A slowdown beyond what a CI step tolerates goes to the owner. Docs: the roadmap limitation, and a roadmap sentence on `utils.ts`. Gates: as G2.

Execution: commit c7002aa0; timing before/after on a one-line change, debug build: `examples/handler/utils.ts` 0.12 s (exit 2) / 0.51 s (exit 0), `examples/handler/handler-with-imports.ts` 0.36 s / 0.51 s; tests "run: a pure helper that gains a cache write breaks the handler that imports it" (exit 2, expected 1), "run: a helper that fails its own analysis is not a root and its importer is compared" (2, expected 1), "run: a changed helper that no handler imports is skipped as unreferenced" (2, expected 0), "run: a change two imports away from a handler reaches the handler" (2, expected 1), "run: a renamed helper that an importer still names by the old path exits 2" (0, expected 2), "run: a deleted helper that a handler still imports exits 2" (0, expected 2), "run: a helper change with no effect change lists the importer as compared and exits 0" (exit 0 with no handler listed), "run: an unchanged file that fails strict checks and imports nothing does not affect a helper verdict" (2, expected 1), and the three tests for the import-depth chain and the unparseable file rule (message or exit differed) failed before the fix; the design is Decision 12(a) with a parse-only `scanSource` (packages/tools/src/precompile_imports.zig), a reverse import graph per side, and CHECK only on the reached handlers; a file that does not parse and names a changed file's stem, when it is a handler candidate and not itself changed, gives exit 2; gates fmt-check of the changed Zig files, test-cli, test-precompile, smoke-v1, test-proof-swallow, test-module-boundary, test, check-spine, test-docs-drift, test-doc-links, test-release-workflow exit 0.

### C1: certificate assurance design study

Observed: the consumer re-derives only `response_total`. `results_checked`, `no_secret_leakage`, and `capability_bounded` enter at `tested`. `docs/verification.md:574` names `results_checked` as the next family. `capability_policy.zig` decodes the residual runtime allowlists, not a capability ceiling. The executable graph commits the capability matrix only as a digest. The proof IR lowers `capability_call` only for guarded calls with an unresolved resource.

Per family, the kernel would need:

- `results_checked`: Result-binding dataflow with `.ok` narrowing across branches.
- `capability_bounded`: every capability-reaching call lowered with its catalog row, the ceiling in the certificate, and a set-union rule. Its rule is the simplest of the three, but P2 must fix the producer first.
- `no_secret_leakage`: full label propagation with declassifiers and `env.public`. This is the largest.

Decision 8 selects the family. C1 writes the consumer rule, the producer evidence, the mutant that the checker must reject, and the cost. C2 needs a separate owner approval of that design.

Result: the design is [v0.26.0 C2 design](2026-10-28-v0.26.0-c2-design.md). The owner chose Decision 13(a), Option C, and Decision 14(a), on 2026-10-28. A Fable subagent validated the design on 2026-10-28 and found one blocker and four major defects; the lead confirmed them and the design section "Revision 1" resolves all thirteen findings.
