# v0.26.0 R7c-3 a repair plan for every rejection - Plan

## Goal Capsule

- **Objective:** A model that asks for repair help on a rejected handler gets a concrete repair plan for every error the compiler reports, and the verdict says the handler is rejected whenever any error remains.
- **Means:** producers give every error code a help text and tag Result shapes; `pi_repair_plan` reports every production rejection and builds a typed or a help-text plan for each (KTD1 to KTD5).
- **Authority:** this plan, then the R7c-2 plan (`docs/plans/2026-10-29-v0.26.0-r7c-2-plan.md`), then the v0.26.0 plan. The owner decisions below are settled.
- **Stop conditions:** a census difference that this plan does not explain stops the work and goes to the owner. A pin moves outside the set in the Verification Contract: stop and report. An implementer reaches the turn budget: stop and hand back status and open items.
- **Execution profile:** Fable validated this plan (draft 2 takes its findings). Sonnet implements U1 to U4 in order. Opus reviews each diff and runs the gates. After U4, `ce-code-review` covers R7c-2 and R7c-3 together.
- **Who finishes:** commits land on local `main`. The owner pushes and runs `zig build diagnostic-corpus-write` (KTD6).

## Product Contract

### Summary

R7c-2 made `pi_repair_plan` report what the production check reports, but an early stop returns `plans: []`, and after the verifier the tool drops spec, policy, and later canonical errors. R7c-3 closes both gaps. Every production rejection reaches the envelope, and each gets a typed plan when a repair intent or a Result shape makes one possible, and a help-text plan otherwise. A census over the corpus holds this for every error the corpus produces.

### Problem Frame

The owner wants every rejection to carry a repair plan. Over the 182 corpus cases, `zts check --json` reports 151 error diagnostics across 90 codes. Only 27 carry a typed repair intent, and 22 carry no help text at all, across 13 codes (ZTS002, ZTS012, ZTS013, ZTS026, ZTS045, ZTS047, ZTS200, ZTS201, ZTS202, ZTS203, ZTS209, ZTS502, ZTS504). Four Result mistakes lost their typed template in R7c-2, because production stops them before the verifier: `r.ok === true` (ZTS620), `r.foo` (ZTS201), `r.isOk()` (ZTS100), and `return r` (ZTS204).

### Requirements

**Reporting and verdict**

- R1. `pi_repair_plan` reports every production diagnostic in `diagnostics`, except flow codes, which stay witnesses. On the observer path this adds the production diagnostics that are not verifier or flow codes: bool, type, and strict warnings, spec ZTS5xx, POL, the public-helper ZTS6xx, and ZTS7xx.
- R2. Each reported diagnostic keeps its production code, severity, line, and column, so the R7c census can compare the set.
- R3. `ok` is false when any reported diagnostic has error severity, in addition to the R7c-2 conditions (verifier error, requested-goal flow diagnostic, unproven goal).

**Plans**

- R4. Every reported diagnostic with error severity, and every production flow error for a requested goal, has at least one plan that targets its line and column.
- R5. ZTS620, ZTS201, and ZTS204 get the typed Result plan when their subject is a Result: the `check_result_before_value` kind with the shape's summary and a template that names the subject. ZTS100 gets it when the condition calls a member named `isOk` or `isErr`, because the bool checker has no types.
- R6. A diagnostic whose repair intent the apply step supports gets a typed plan whose edit intent names that repair intent.
- R7. Every other error gets a help-text plan: its summary is the diagnostic's help text, `behavioral_change` is true, and its edit intent kind is `manual_edit`, which the apply step reports as unsupported.
- R8. Every error code that the corpus produces carries a non-empty help text in `zts check --json`.

**Consumers**

- R9. The expert loop, `pi_goal_candidate`, and `auto_repair` keep working: a help-text plan is never applied automatically, never shown as a compiler-authored fix, and never ends the compiler-repair lane. A typed plan with an empty template is shown with its summary and intent name.

**Measurement**

- R10. The R7c census compares every non-flow production diagnostic, and fails when a requirement-R4 error has no plan. It reports per-tier plan counts and the count of distinct error codes it observed, and asserts them as literals.

### Key Decisions

- **Every rejection gets a repair plan, enforced by a census, with an allowlist row that states why for any code no plan can reach.** (session-settled: user-directed — chosen over mapping only the four Result codes back to their old templates, and over reverting early stops to the bare checkers: the owner wants every rejection to carry a plan, and the bare route restores two analyzer routes that Decision 2 removed.) Governs R4, R10.
- **Two tiers: typed where a repair intent or template exists, help text everywhere else, and help text written for every error code that lacks it.** (session-settled: user-directed — chosen over a typed template for each of the 148 catalog codes, and over help-text plans with only the four Result shapes typed: the typed-for-all bar costs several times the work, and help-only names no edit for most codes.) Governs R5, R6, R7, R8.
- **R7c-2's production route and Decision 46(a)'s early-stop diagnostics stay; R7c-3 adds plans to them.** (session-settled: user-directed — chosen over reverting the R7c-2 move: the owner kept the move and asked for plans on top.) Governs R1, R4.

### Scope Boundaries

- `pi_goal_check` and `zts_expert_narrow` keep their envelopes. They report property goals and witnesses, not repairs.
- The rule registry (`packages/zts/src/rule_registry.zig`) does not change, so `policyHash` does not move. Help text and Result tags change at the producers only.
- No new `RepairIntent` member. `RepairKind` and `EditIntentKind` in `packages/zts/src/repair_plan.zig` gain members, which no hash covers.
- The apply step does not learn new intents. Intents with no `repair_apply.RepairKind` entry get the help-text tier: `add_capability_declaration`, `add_spec_assertion`, `lead_with_spread`, `widen_signature_drop_spread`, `declare_boundary_type`, `insert_semicolon`, `replace_effectful_ternary_with_match`, `replace_chained_ternary_with_match`, and `canonicalize_capability_key_alias`. `replace_chained_ternary_with_match` is a `StatementKind`, which `executeSemanticPlan` never applies.
- A flow error for a goal the caller did not request stays out of R4, because the caller narrowed the goals.
- Considered and not built: a pi-side per-code help table. It would keep the corpus goldens still, but `zts check` users would still get no help for those codes, and the tool would no longer say what `zts check` says.
- Codes that no corpus case produces stay governed by `scripts/corpus-uncovered.allow`, which already gives each a reason. R7c-3 does not add corpus cases.

## Planning Contract

### Key Technical Decisions

- KTD1. **Help text lives at the producer.** Each construction site that leaves help null gets a fixed help string that never echoes a source literal, because a literal can carry a secret (`docs/solutions/security-issues/a-deny-list-in-two-tools-left-the-other-workspace-tools-reading-secrets.md`). The sites:
  - ZTS002 (`.unexpected_token`) comes from about 27 `errorAtCurrent` sites. `ParseErrorList.addErrorAt` in `packages/zts/src/parser/error.zig` fills one fixed default suggestion for `.unexpected_token` when a site sets neither `suggestion` nor `expected`.
  - ZTS012, ZTS013, ZTS026, ZTS045, ZTS047 each get a per-site string in `packages/zts/src/parser/parse.zig`.
  - ZTS200: `addTypeMismatch` in `packages/zts/src/type_checker.zig`, whose `undefinedSourceHelp` leaves help null for every corpus case, plus the readonly-property and narrow-union sites that no corpus case reaches.
  - ZTS201, ZTS202, ZTS203, ZTS209 at their `type_checker.zig` sites.
  - ZTS502 and ZTS504 at their spec producers (`spec_discharge.zig` or `contract_types.zig`).
- KTD2. **Result shapes travel as in-process fields, and the subject name is owned.** `diagnostic_projection.Diagnostic` and `JsonDiagnostic` gain an optional `result_shape` and an optional `result_subject`. `writeDiagnosticJson` does not serialize them, so `zts check` output moves only by KTD1. `ResultShape` is re-exported on the curated surface of `packages/zts/src/root.zig`, so `packages/tools` names it without a boundary row. The checker takes the subject from the atom table, which the check frees before it returns, so `fromCheckerDiagnostic` copies it into the `JsonDiagnostic` allocator with a `result_subject_owned` flag, and `JsonDiagnostic.deinit` frees it, as it does for `suggestion_owned`. Producers set the fields:
  - the strict checker for ZTS620 when the compared operand is a Result's `ok` member (`unrecognized_guard`);
  - the type checker for ZTS201 (`unknown_member`) and ZTS204 (`returned`) when `TypePool.isResultRecord` holds for the subject type;
  - the bool checker for ZTS100 (`method_call`) when the condition is a call of a member named `isOk` or `isErr`.
- KTD3. **Precedence is decided in `pi_repair_plan`; the constructor in zts is pure.** `repair_plan.zig` gains a constructor over plain fields (code, line, column, help, Result shape and subject, and a `supported_intent: ?RepairIntent`). `pi_repair_plan` fills `supported_intent` only when `repair_apply.RepairKind.fromString(intent.asString())` returns a value, because zts cannot import `repair_apply`. Precedence for one diagnostic: Result shape (R5), then a supported intent (R6), then help text (R7). A typed plan suppresses the help-text plan for that diagnostic. Verifier and flow plans keep their present constructors. A requested-goal flow error with no flow plan gets a help-text plan from its production diagnostic.
- KTD4. **New plan kinds and an intent field.** `RepairKind` gains `apply_repair_intent` and `follow_diagnostic_help`. `EditIntentKind` gains only `manual_edit`. `EditIntent` gains `repair_intent: ?RepairIntent = null`. For an R6 plan the constructor sets it, and `writePlan` writes `repair_intent.asString()` as the JSON `kind`, because `pi_apply_repair_plan.parseRepairIntent` reads that string as the intent name.
- KTD5. **Consumers treat `manual_edit` as advice.**
  - `pi_apply_repair_plan` reports `manual_edit` as `unsupported_repair_intent`, as it does today for unknown kinds, so `pi_goal_candidate` continues instead of failing. The stale `unsupportedResult` text ("v1 only supports ...") is corrected.
  - `pi_goal_candidate` reports `no_repair_plans` when no plan has an applicable kind, not only when the list is empty.
  - `auto_repair.buildRetryBlock` skips `manual_edit` plans, and for an `apply_repair_intent` plan with an empty template it prints the summary and the intent name.
  - `autoloop.applyPlans` already skips `behavioral_change: true`.
- KTD6. **The corpus goldens move once, by the owner.** KTD1 changes `suggestion` in the 22 goldens that hold one of the 13 codes: 15 under `tests/corpus/check/bad/` and 7 under `tests/corpus/parse/bad/`. `diagnostic-corpus-write` is a human action (`build/corpus.zig`), so the implementer does not run it. `test-diagnostic-corpus` fails on exactly those goldens until the owner runs the write step, and the U1 commit lists them. The fixture `packages/tools/tests/fixtures/generic-intersection/reject_member_17.golden.json` also pins a ZTS203 with a null suggestion. It is not a human-only write, so U1 regenerates it from `zts check --json`.
- KTD7. **The census grows in two steps.** U3 drops the verifier-only filter in the R7c census (`packages/pi/src/tools/common.zig`) and compares every production diagnostic except those whose code `DiagnosticProjection.allCodes()` lists with `source == .flow`, so each commit stays green. U4 adds the R4 plan check, the per-tier and per-code counts, and their literals. A per-code universe over `zts.DiagnosticCatalog` is not repeated: the corpus gate already requires every catalog code to have a corpus case or a reasoned row in `scripts/corpus-uncovered.allow`.

### Assumptions

- R1 widens the R7c-2 envelope, and R3 widens its verdict. A rejection the tool does not report cannot carry a plan, and a reported error must not read as a pass. The R7c-2 KTD5 verifier-only comparison retires.
- The 22 help-less diagnostics in 13 codes are a corpus measurement. KTD1 fixes every null-help site of those codes, not only the reached ones. A site of another code that no corpus case reaches can still emit null help. R8 is scoped to codes the corpus produces.
- The ZTS309 test in `pi_repair_plan.zig` that asserts no `diag_002` stays true only while its source carries no other diagnostic. U3 confirms it.
- The census literals are measured after U4 and asserted as literals.

### Sequencing

U1 writes the help text, because the help-text tier and the census depend on it. U2 adds the Result tags. U3 builds the plans, widens the envelope and verdict, and widens the census comparison. U4 updates the consumers and adds the census plan check. U1 and U2 touch `packages/zts` and `packages/tools`. U3 touches `packages/zts` (`repair_plan.zig`) and `packages/pi`. U4 touches `packages/pi`.

## Implementation Units

### U1. Help text for every error code the corpus produces

- **Goal:** every error diagnostic in the corpus carries a non-empty help text.
- **Requirements:** R8. KTD1, KTD6.
- **Dependencies:** none.
- **Files:** `packages/zts/src/parser/error.zig`, `packages/zts/src/parser/parse.zig`, `packages/zts/src/type_checker.zig`, `packages/zts/src/spec_discharge.zig` or `packages/zts/src/contract_types.zig`, `packages/tools/tests/fixtures/generic-intersection/reject_member_17.golden.json`, tests beside each changed producer.
- **Approach:**
  1. Run `zts check --json` over `tests/corpus` and list every error diagnostic with a null `suggestion`, by code and site.
  2. Apply KTD1 at each site.
  3. Regenerate `reject_member_17.golden.json` from `zts check --json`. Do not run `diagnostic-corpus-write`. List the 22 moved corpus goldens in the commit.
- **Execution note:** write one failing test per producer family first: a source that triggers the code and asserts the exact help string.
- **Patterns to follow:** existing help strings in `bool_checker.zig` and `strict_checker.zig`. `addErrorFmt` with a suggestion in `parse.zig`.
- **Test scenarios:**
  - A source with an invalid number literal (ZTS012) reports the help string written for it.
  - A statement without its semicolon (ZTS047) reports its help string.
  - An unexpected token from an `errorAtCurrent` site (ZTS002) reports the per-kind default.
  - `const n: number = "a";` (ZTS200 through `addTypeMismatch`) reports its help string.
  - A call with the wrong argument count (ZTS202) reports its help string.
- **Verification:** the corpus run lists no error diagnostic with a null suggestion. `test-zts` and `test-generic-intersection-cli-matrix` pass. `test-diagnostic-corpus` fails only on the 22 goldens.

### U2. Result-shape tags on the four early-stop codes

- **Goal:** ZTS620, ZTS201, ZTS204, and ZTS100 carry a Result shape and an owned subject name per KTD2.
- **Requirements:** R5. KTD2.
- **Dependencies:** none.
- **Files:** `packages/zts/src/root.zig` (re-export `ResultShape`), `packages/zts/src/diagnostic_projection.zig`, `packages/zts/src/strict_checker.zig`, `packages/zts/src/type_checker.zig`, `packages/zts/src/bool_checker.zig`, `packages/tools/src/json_diagnostics.zig`, tests beside each.
- **Approach:**
  1. Add the two optional fields to the projected and JSON diagnostic types, defaulting to null, with the ownership of KTD2, and leave `writeDiagnosticJson` unchanged.
  2. Set them at the four producer sites.
- **Patterns to follow:** the verifier's `result_shape` field. `TypePool.isResultRecord`. `suggestion_owned` in `json_diagnostics.zig`.
- **Test scenarios:**
  - `if (r.ok === true)` on a Result `r` projects `unrecognized_guard` and subject `r`.
  - `r.foo` on a Result `r` projects `unknown_member` and subject `r`. `p.foo` on a plain record projects no shape.
  - `return r` of a Result `r` projects `returned` and subject `r`.
  - `if (r.isOk())` projects `method_call` and subject `r`.
  - The JSON diagnostic for `r.foo` still names `r` after the check that built it has returned and freed its atom table.
  - `zts check --json` output for each of these sources is byte-identical before and after the unit.
- **Verification:** `test-zts`, `test-zts-cli`, `test-zts-layering`, and `test-module-boundary` pass. `test-contract-golden` passes and `test-expert-golden` fails only on its known W pins.

### U3. A plan for every reported error in `pi_repair_plan`

- **Goal:** the envelope reports every production rejection, gives each error a plan, and sets `ok` per R3.
- **Requirements:** R1, R2, R3, R4, R5, R6, R7. KTD3, KTD4, KTD7 (first step).
- **Dependencies:** U1, U2.
- **Files:** `packages/zts/src/repair_plan.zig`, `packages/pi/src/tools/pi_repair_plan.zig`, `packages/pi/src/tools/common.zig`, tests in `pi_repair_plan.zig`.
- **Approach:**
  1. Add the constructor of KTD3 and the kinds and field of KTD4.
  2. On the early-stop path, write a plan after the production diagnostics for each error.
  3. On the observer path, append the non-verifier, non-flow production diagnostics and their plans after the verifier ones, and add help-text plans for requested-goal flow errors that have no flow plan.
  4. Set `ok` per R3. Keep ids stable: diagnostics `diag_NNN` and plans `rp_NNN` in report order.
  5. In the R7c census, drop the verifier-only filter and exclude flow codes from the expected set (KTD7).
- **Execution note:** restore the four early-stop tests first as failing tests that expect the typed Result plan, then implement.
- **Patterns to follow:** `writePlan` and `concreteTemplate` in `pi_repair_plan.zig` for the Result template. `repair_apply.RepairKind.fromString` for the supported intents.
- **Test scenarios:**
  - The four early-stop tests (`ok === true`, unknown member, method call, returned Result) each report the production code and a `check_result_before_value` plan with the shape's summary and a template that names `r`.
  - A compound assignment (`x += 1`) refused with ZTS613 gets an `apply_repair_intent` plan whose `edit_intent.kind` is `replace_compound_assign_with_explicit`.
  - `const n: number = "a";` (ZTS200) gets one `follow_diagnostic_help` plan whose summary is the U1 help text and whose `edit_intent.kind` is `manual_edit`.
  - A handler that passes the verifier and fails a spec assertion (ZTS5xx) reports that diagnostic, a plan, and `ok: false`, where R7c-2 reported nothing and `ok: true`.
- **Verification:** the new tests pass. `test-expert-app` fails only on the two known W tests, with the widened census passing.
