# v0.26.0 C2 design: consumer re-derivation of `results_checked`

Scope: read-only study, run on 2026-10-27. The appendix holds the source of each false-proof probe.

Labels used below. "Observed" means I read the code or ran a command. "Inferred" means I
reasoned from observed facts and did not run a check. "Estimate" means an unmeasured number.

Probe caveat: the probes ran `zig-out/bin/zts` built at 19:59 on 2026-10-27. The last commit is
at 19:50, and the working tree held uncommitted edits from another agent
(`packages/tools/src/precompile_check_tests.zig`, `packages/tools/src/precompile_imports.zig`)
when I looked. The probe results describe that binary. Re-run them on a clean build before
any fix unit cites them.

## Summary and recommendation

Recommended: Option C, a structural dominance rule over the existing proof IR. It adds five node
tags, one rule, one rule family, and one kernel pass. The pass needs no new scratch, no fixpoint,
and no change to the totality fold. It refuses what it cannot express: a rebound Result, any use of a
Result binding other than a guarded read, and a read inside a nested function that is guarded only
outside it. It covers the whole program, not only the handler body.

Estimated cost: about 1400 lines (kernel about 260 plus 350 tests, producer about 600 plus 300 tests,
glue and gates about 100). Stop rule: stop if any Result-free tracked file changes `ir_root`, or if the
kernel and the verifier disagree on any of the 19 Result-using tracked files without a named
false proof as the cause.

Decisions the owner makes: Decision 13 (kernel rule shape) and Decision 14 (what happens to the
producer false proofs). Both are at the end. The owner chose 13(a) and 14(a) on 2026-10-28.

## Revision 1: binding changes after the Fable validation (2026-10-28)

A Fable subagent validated this design on 2026-10-28 against commit 02147a30. The lead confirmed
finding 1 and the `.errors` alias in the code. Where this section and a later section disagree, this
section is the authority. The finding number is in brackets.

Tags. The alphabet is six tags, 9 to 14:

| Tag | aux | Meaning |
| --- | --- | --- |
| 9 `result_def` | ordinal | `const b = <Result export call>` |
| 10 `result_guard_ok` | ordinal | the `if` condition is exactly `b.ok` |
| 11 `result_guard_err` | ordinal | the `if` condition is exactly `!b.ok` |
| 12 `result_read_ok` | ordinal | `.value` or `.unwrap`, as a member or a literal computed key |
| 13 `result_read_err` | ordinal | `.error` or `.errors`, as a member or a literal computed key |
| 14 `result_escape` | ordinal | every other use |

Ordinals [5]. An ordinal is numbered per `var_decl` binding and keyed on `(scope_id, slot)` of
`ir.BindingRef`. It is never keyed on the name. Two `const r` in sibling blocks or sibling functions
get two ordinals.

Rule 2, consolidated [2, 3, 10]. Each reference to a Result binding is classified as follows. Nothing
else is a read.
- `b.ok` in any position emits no node. It reads a boolean and cannot crash.
- The two exact condition forms `if (b.ok)` and `if (!b.ok)` are guard heads.
- `b.value`, `b.unwrap`, `b["value"]`, `b["unwrap"]` emit `result_read_ok`.
- `b.error`, `b.errors`, and the two literal computed forms emit `result_read_err`, except as the left
  operand of `??` or as the object of `?.`, where they emit nothing. On an ok Result `.error` is
  `undefined`, so `b.error ?? x` gives `x` and no payload [11].
- An argument at a position that a builtin export declares `param_types = .result` emits nothing
  (rule 3; the five exports are `mapResult`, `mapError`, `andThen`, `orElse`, `unwrapOr`, and each tests
  `ok` before it reads `value` [9]).
- Every other position emits `result_escape`: alias, call argument, return, object or array member,
  spread `{ ...b }`, a computed key that is not a literal, a method call on `b` (`b.isOk()`,
  `b.unwrapOr(0)`, `b.map(f)`), `collectAll([b])`, a closure capture without a read, and a member read
  on a call with no binding.

Upvalues [4]. A reference inside a nested function resolves through the closure's upvalue table to
the declaring `(scope_id, slot)`. Do not copy `bindingOf` in `handler_verifier.zig`, which resolves an
upvalue by name and gives up when two declarations share it. Where the IR cannot resolve an upvalue,
any upvalue reference whose name matches a Result binding emits `result_escape`.

Kernel pass `checkResults`, revised:
- Arm totality [1]. The pass reads totality from a second fold that does not include `self.declared`.
  `foldTotality` ORs in `self.declared`, which `markDeclared` sets from a `trusted` node edge on
  `response_total`. Under that fold a hand-built certificate with `sequence[result_guard_err(b),
  branch[plain]]`, a trusted node edge on the `plain`, and a read after the `if`, is accepted. The new
  fold adds one bit array of `max_ir_nodes` bits to `scratchBytes`.
- Arm pattern with polarity [2]. A `result_read_ok(b)` is covered in the then arm of
  `result_guard_ok(b)` and in the else arm of `result_guard_err(b)`. A `result_read_err(b)` is covered
  in the then arm of `result_guard_err(b)` and in the else arm of `result_guard_ok(b)`.
- Early-return pattern with polarity. An earlier sibling wrapper with `result_guard_err(b)` whose then
  arm is total in the derived fold covers a later `result_read_ok(b)`. An earlier sibling wrapper with
  `result_guard_ok(b)` whose then arm is total covers a later `result_read_err(b)`.
- The rest of the pass is unchanged: refuse any `result_escape`, a second `result_def` of one ordinal, an
  ordinal at or above 64, and a guard whose parent is not a two-child `sequence[guard, branch]`. The walk
  stops at a `function` node.

Other changes:
- `countDisclosedEdges` [6]: add `trusted.len()` once when any required property depends on the
  trusted edges, not once per property. The design text below said "undercount"; the correct word is
  overcount. The pin `disclosed_edges == 3` in `checker.zig` stays. With the opcode cap, every
  certificate reports `results_checked` as `trusted` in `proofs verify` and in the server log. That is
  the intended grade, and the docs say so.
- Rule 5 [12]: `ProofIr.nodeFor` returns `null` when `source == null_node`, so no translation witness
  attaches to an event node. Rule 5a is replaced: a `var_decl` leaf is never a `capability_call`
  (`guardedIndex` resolves only `.call` and `.method_call`), so the lowering puts `result_def` first
  under its leaf, in a fixed child order.
- Verifier parity (R3). R3 refuses the same shapes as the lowering: the seven in section 2, the
  duplicate-name closure (`p_closure_dup2`), spread (`p_spread`), a non-literal computed key
  (`p_computed`), and the Result method forms. No tracked file uses a method form. The parity gate names
  each difference by one of these causes.
- New kernel fixtures beside section 4: (14) the declared-arm certificate of finding 1 is refused;
  (15) `if (!r.ok) { r.errors }` is accepted and `r.value` in the same arm is refused; (16) a
  `result_read_err` in the then arm of `result_guard_ok` is refused. Each has a source-text mutant:
  the derived fold replaced by `self.total`, and the polarity test removed.
- Cost [13]: about 1700 to 1900 lines, an estimate that includes R3 and the parity gate.

Corpus effect. Five tracked files read `.errors` in the err arm of `if (!x.ok)`:
`examples/modules-all/modules_all.ts`, `examples/sql/sql-crud.ts`, `tests/validate/format_handler.ts`,
`packages/tools/tests/fixtures/contract/modules_all.ts`, and the DeepSeek `validate-body` expected
handler. `examples/patterns/result-combinators.ts` reads `empty.ok` outside a guard. Under Revision 1
each of them is accepted.

## 1. What the certificate carries today

Observed.

Proof IR. The type is `ProofIr` in `packages/zts/src/proof_ir.zig`. Its nodes have `id`, `tag`,
`parent`, `first_child`, `child_count`, `digest`, `source`, and `aux`. Ids are breadth first, so the
children of a node are one contiguous id range. The tags are seven: `function`, `sequence`, `branch`,
`loop_node`, `return_node`, `plain`, `capability_call`. The kernel copy is `ps.NodeTag` in
`packages/proof-checker/src/proof_system.zig`. Wire ordinal 8 is retired, so a new tag starts at 9.
Everything that is not control flow collapses to a `plain` leaf. A condition expression is not in the
IR at all.

Lowering. `Lowerer.build` in `proof_ir.zig` lowers the whole program from the root, not only the
handler. Sibling top-level functions become `function` nodes. The one place where an expression
gets structure is `leaf` plus `containsRelevantCall`. They descend into an expression only along paths
that reach a guarded call, so a handler with no guarded call keeps its old proof identity. The
`if_stmt` arm already wraps `sequence[condition, branch]` when the condition holds a guarded call, so
`branch` keeps exactly two children. `lower` is called with the program root from
`packages/tools/src/precompile.zig` (`zts.buildProofEvidence`).

Wire. `IrNode` in `packages/proof-checker/src/certificate.zig` is a 56 byte record: id, tag (u16),
`is_handler`, parent, first_child, child_count, digest (32 bytes), `aux` (u32). `NodeTag.usesAux`
is true only for `capability_call`, and the decoder requires `aux == 0` for every other tag.
`irRootFromTable` folds all of it into `identity.ir_root`, which is also a graph member digest
checked in `bindExecutableGraph`.

Obligations. The producer emits one obligation per `Property` (eight). The kernel reconstructs the set
itself in `checkObligationSet`. Only `response_total` has the entry function as its subject.

Evidence. An evidence record has `obligation_index`, `edge`, `rule`, `node_id`, `aux`. For
`response_total` the producer emits `proved` with a totality rule (`appendTotalityEvidence` in
`packages/runtime/src/proof_certificate.zig`), then `translation_validated` rows for emissions and
jumps. For every other property it emits one row: `tested` when
`DischargedProperties.holds(property)` is true, else `not_established`, with `rule = null` and
`node_id = 0` (same file, the `else` arm of `build`).

Kernel check of `response_total`. `checkIrShape`, then `markDeclared`, then `foldTotality` (one reverse
sweep, bit per node, `self.total`), then `checkTranslation`, then `checkEvidence`. `classify` admits a
`proved` edge only when `rule.family() == .totality and property == .response_total`. A `proved` rule
must equal `ruleAt(node)`, else `rule_premise_unmet`. `checkEvidence` then refuses any non-refused
claim on `response_total` whose entry function is not total as `fabricated_property` with
`recertifiable = false`. Everything else enters at `tested` unchecked.

Rules and families. `Rule` has eight members (1 to 4 totality, 5 to 8 translation). `RuleFamily` is
`{ totality, translation }`. `Property.consumerChecked` is true only for `response_total`
(`consumerCheckedCount() == 1`, asserted in `packages/runtime/src/proof_ratchet.zig`).

Policy. `policy.zig` `production_requirements`: `response_total` at `.trusted`, `results_checked` at
`.tested`, `no_secret_leakage` at `.tested`. The ladder in `verdict.zig` is `proved(0) <
translation_validated < solver_assumed < tested < trusted(4)`, and `atLeastAsStrongAs` means "index
is at most the floor". So `trusted` is the weakest grade, and a `proved` edge already passes the
`.tested` row.

Budget and scratch. `limits.zig`: `max_ir_nodes` 65536, `max_depth` 256, `max_work` 8,000,000.
`scratchBytes` is a fixed formula: two bit arrays, a u16 depth table, a u64 range stack.

Certificate scope. Observed: `compileHandler` returns early into `compileMultiModule` when the entry
file has file imports (`packages/tools/src/precompile.zig#compileHandler`), and `compileMultiModule` returns no `proof_evidence`.
So a handler with file imports has no certificate, and helpers in other files are out of scope by
construction. Inferred: every certified artifact is one source file, so the IR sees all user code that
the handler can run.

Model visibility. Observed: no file under `tooling/`, `packages/tools/tests/fixtures/`, `scripts/`,
`packages/pi/src`, or `docs/*.md` names `ir_root`, `proof_ir_digest`, or `certificate_digest`. Inferred:
certificate bytes are not model-visible, so the change moves no replay pin. It does move the
`proof_ir` graph member digest and the certificate digest of every artifact whose IR gains a node.
Which gates pin an artifact digest needs to be measured, not assumed (the unit runs the gate list).

## 2. What the producer knows about Results

Observed, with file and symbol.

Property chain. `packages/tools/src/precompile.zig#compileHandler` sets `verify_info.results_safe = error_count == 0` and then
`result_safe = true` after the verifier ran with no errors. two sites in `precompile_check_run.zig`
do the same for `zts check`. `packages/runtime/src/build_command.zig#dischargedProperties` maps
`properties.result_safe` to `DischargedProperties.results_checked`, which becomes a `tested` edge.
So `results_checked` means "the verifier found zero errors of any kind", which is wider than the
property text. `contract_runtime.zig` gates the runtime `result_safe` on
`verdicts.accepted(.results_checked)`.

Result sources. `lookupTrackedFunction` in `handler_verifier.zig` reads `entry.func.returns == .result`
from `builtin_modules.findExport`. `scanImports` records only builtin imports, keyed by import slot.
`resultProducingCallSource` accepts only a `var_decl` whose init is a direct call to such a slot.
Exports with `.returns = .result` (from `rg`): `parseJson`, `parseJsonBytes`, `stringifyJson`, `ok`,
`err`, `mapResult`, `mapError`, `andThen`, `orElse`, `collectAll`, `bytesFromOctets`, `sliceBytes`,
`concatBytes`, `decodeUtf8`, `decodeBase64`, `dictFromEntries`, `validateJson`, `validateObject`,
`coerceJson`, `decodeJson`, `decodeForm`, `decodeFormMultipart`, `decodeQuery`, `jwtVerify`,
`rateCheck`, `sseEvents`. The list is a union of name scans, so it may include a name that is
not a Result export in this tree; the lowering must read the registry, not this list.

Flag logic. State is `BindingState.ok_checked` per `(scope_id, slot)` key, plus the
`checked_journal` of `CheckedChange` entries. In `walkForResultsAndRefs`:
- A block takes `journalMark` and `journalRestore`, so a guard holds to the end of its block.
- Positive guard (`extractResultOkCheck`, forms `b.ok`, `b.isOk()`, `b.ok === x`): set true, walk the
  then arm, set false, walk the else arm with false. The unconditional reset to false also drops a
  check that an outer guard had set.
- Negated guard (`extractNegatedResultOkCheck`, forms `!b.ok`, `b.isErr()`, `b.ok !== true`,
  `b.ok === false`): walk the then arm. If `stmtReturnsQuick(then) == .always`, set true for the rest
  of the block. With an else arm, set true while it walks, and reset only if the then arm does not
  always return.
- `stmtReturnsQuick` is a subset of the kernel totality fold: return, block with an always-returning
  statement, `if` with both arms always returning. Loops and `match` never count.
- Loops: `killFlagsAssignedIn(for_iter.body)` runs only in the `.for_of_stmt` arm, before one walk of
  the body. It clears the flag of every binding assigned anywhere under the body, including inside
  closures and branches. The kill survives the loop. `killCheckedFlag` rewrites the journal so no
  restore revives the old check.
- Closures: `walkNestedFunctionBody` clears every Result flag for the walk. A kill inside survives.
- `assert`: the condition and error expression are walked for references only. No narrowing (plan R0
  item 8). `match` arms and ternary arms do not narrow either.
- Reads: `checkResultValueAccess` fires for `.value` and `.unwrap`, and
  `checkResultValueAccessComputed` for the literal keys `"value"` and `"unwrap"`. `.error` is not
  checked today (plan A4).
- Reassignment: `handleOptionalReassignment` kills the Result flag of any assigned identifier.
- Scope: `verify(handler_func)` walks the handler body and nested functions only.

## 3. Design options

All three options certify one thing: given the IR the producer wrote, every Result read is guarded.
None of them certifies that the IR is a faithful lowering of the source, or that the bytecode runs the
IR. That relation is the same one totality already trusts (the `opcode` trusted edge, and the
unchecked claim that a `return_node` is a return). D-005 keeps IR-to-bytecode out of the kernel, so
this design does not change that. The new gain is real but narrower than "the consumer proves it":
the kernel stops accepting the verifier's flag logic on faith, and the lowering becomes a second
independent recognizer. Inferred: a recognizer bug that the lowering shares with the verifier
(copying `extractResultOkCheck`) would pass both, so the lowering must be written from the four
canonical guard forms, not from the verifier's code.

### Option A: producer lowers events, kernel runs a must-dataflow

New tags: `result_def`, `result_guard_ok`, `result_guard_err`, `result_read`, `result_kill`,
`result_escape`. `aux` is a binding ordinal. Kernel state is a set of checked ordinals (a u64, so at
most 64 bindings), join is intersection, an always-returning arm contributes the full set.

Kernel algorithm, bottom up in one reverse sweep beside `foldTotality`, with two u64 per node:
`need(n)` is the set of ordinals that must be checked on entry, and `gen(n)` is the set certainly
checked on exit (full set for a total node). A sequence folds children in order with a running `gen`.
Guarded branch `b`, ok polarity: `need = (need(then) minus b) union need(else)`, and
`gen = (gen(then) union b) intersect gen(else)`. Err polarity swaps the arms. A kill removes from
`gen`. A loop sets `need(loop) = need(body)` and `gen(loop) = empty`, and it fails if
`need(body)` meets the kill set of the body. Every `function` node must end with `need == 0`.

Budget: one visit per node plus a constant number of u64 operations, so at most
about 65536 times a small constant units. Scratch: 2 times 8 bytes times `max_ir_nodes` = 1 MiB more
in `scratchBytes` (estimate from the sizes, not measured), or a depth stack if the pass is a
pre-order walk. Kill and loop support is the reason to choose A.

Cannot express: Results in closures guarded outside (refused, same as the verifier), helpers across
modules (no certificate), `match` and `assert` narrowing (the verifier does not narrow either, so
there is nothing to match). Must refuse: escape, rebinding when the loop rule cannot be satisfied,
more than 64 bindings.

### Option B: producer emits a per-read witness, kernel checks dominance

New section: one record per read holding the read node id and the id of the dominating guard node.
The kernel checks that the guard dominates the read by shape, and that no kill of the binding lies
between them. The kill check needs a scan between two points of a tree whose ids are breadth first, so
it costs a subtree walk per read (quadratic in the worst case). B adds a new section (schema and
`SectionTag` change, a new count limit, new canonical-order rule) and still needs the escape and
closure rules. It is worse than A on wire size and not better on algorithm. Not recommended.

### Option C (recommended): structural dominance, single definition, default deny

IR change (no schema or record-size change):

| Tag | aux | Meaning | Placement |
| --- | --- | --- | --- |
| 9 `result_def` | ordinal | `const b = <Result export call>` | child of the declaring `plain` leaf |
| 10 `result_guard_ok` | ordinal | the `if` condition is exactly `b.ok` | first child of a wrapper `sequence[guard, branch]` |
| 11 `result_guard_err` | ordinal | the `if` condition is exactly `!b.ok` | same wrapper |
| 12 `result_read` | ordinal | `.value`, `.unwrap`, or `.error` (not under `??` or `?.`) | child of the enclosing statement leaf, source order |
| 13 `result_escape` | ordinal | any other use of `b`, including any assignment, alias, call argument, return, object member, closure capture without a read | same |

Choice for the branch condition, named as the advisor asked: reuse the existing wrapper
`sequence[condition, branch]` that the `if_stmt` arm of `Lowerer.build` already builds, and put the
guard node first in it. Rejected alternative: a new `branch_on_result` tag that totality treats as
`branch`. It would touch `deriveTotality` and `ruleAt` in the producer and `foldTotality` and `ruleAt` in
the kernel, so it puts the one rule the kernel already proves at risk. The wrapper changes none of the
four totality rules, because a sequence is total when any child is total and the branch child is.
Cost: one extra nesting level, and the kernel pattern looks into the wrapper.

Lowering rules (default deny, whole program):
1. Classify bindings itself. A binding is a Result when its `var_decl` init is a direct call whose
   callee resolves to a builtin import with `returns == .result` (same registry as `scanImports`,
   separate code). It descends along paths that reach such a binding only, the pattern of
   `containsRelevantCall`, so a Result-free program lowers byte for byte as today.
2. Every `IrView.expressionChildren` reference to a Result binding is classified. Use
   `expressionChildren` in the default arm, not `forEachSubNode`, because AGENTS.md names the
   spread-operand miss as the usual fail-open of a hand-written walk. A reference is a `result_read`
   when it is the object of `.value`, `.unwrap`, or `.error`, a guard head when it is the object of
   `.ok` in exactly the two condition forms, and a `result_escape` in every other position.
3. A Result passed as an argument of a builtin export whose binding declares that argument position as
   `param_types = .result` is a safe consumer (`unwrapOr`, `mapResult`, `andThen`, `orElse`, `mapError` in
   `zttp:result`). The lowering reads that existing binding data and emits no node for such an argument.
   No new binding field is added, so the module manifest hash does not move (decided 2026-10-28). The kernel has no combinator concept, because the kernel is a leaf and cannot read
   bindings. The trust sits in the lowering, where it already sits for every other classification.
   `result-combinators.ts` is the only corpus file that needs it. Without this rule that file stops
   proving `results_checked`.
4. A direct member read on a call (`validateJson(...).value`) is a `result_escape`. The ordinal of a
   bindingless escape is 0 and carries no meaning, because any `result_escape` rejects whatever its
   ordinal is. Probe: `p_chain.ts`.
5a. `leaf` returns `capability_call` before it collects children, so one node cannot be both a
   `capability_call` and the parent of a `result_def`. Observed: no row of the residual catalog
   (`docs/verification.md`, `zttp:env`, `zttp:fetch`, `zttp:cache`, `zttp:sql`) is a `returns = .result`
   export today. The lowering must refuse (not lower) a node that is both, so a future catalog row
   cannot silently drop the definition.
5. Event nodes carry a `source` of `null_node`-like sentinel so `ProofIr.nodeFor` cannot hand an
   emission to them. Otherwise translation witnesses of Result-bearing handlers could re-attach to the
   new nodes. Needs a unit test.

Kernel pass `checkResults` (new, in `checker.zig`; runs only when the certificate claims the
`proved` edge with the new rule):
1. One forward scan. Reject if any node is `result_escape`. Reject if an ordinal is `result_def`
   twice (single definition). Reject if any aux is at or above `limits.max_result_bindings` (64).
   Reject a guard whose parent is not a `sequence` of exactly `[guard, branch]`.
2. For each `result_read` of ordinal `b`: it needs a `result_def(b)`. Walk up the parent chain at most
   `max_depth` steps. Stop with failure at a `function` node (a closure never inherits a check).
   Succeed when either pattern holds:
   - Arm pattern. The chain passes through an arm `a` of a `branch` `br` whose parent is a wrapper
     with guard `g` on `b`. `g` is `result_guard_ok` and `a` is the first child of `br`, or `g` is
     `result_guard_err` and `a` is the second child.
   - Early-return pattern. The chain passes through a child `c` of a `sequence` `p`, and an earlier
     sibling `q` of `c` is a wrapper whose guard is `result_guard_err(b)` and whose branch's first
     child is total in `self.total` (already computed by `foldTotality`).
3. Verdict. A claimed `proved` results edge with a failing pass is `fabricated_property` with
   `recertifiable = false`, the same shape as the totality check in `checkEvidence`. A `tested` claim
   is not run in phase 1.

Why single definition is enough here. With one definition per ordinal, a guard that dominates a read
stays valid, so the kernel needs no kill set, no loop fixpoint, and no state between guard and read.
Inferred from the sweep: all 32 corpus bindings are single-definition `const`. A guard inside a loop
body does not dominate code after the loop, because the ancestor walk never leaves the body sequence.

Budget and scratch. Cost per read is the chain length times the siblings scanned, and each scanned
child spends 1 unit. Exhaustion rejects as `work_budget_exhausted`, which is a refusal, not an
acceptance. Worst case is quadratic in nodes but bounded by `max_work`. No scratch growth:
`self.total` and `self.depths` already exist. The `defined` set is one u64 on the stack.

Alphabet and wire impact:
- `NodeTag` 9 to 13, and `usesAux` true for them. Ordinal 8 stays retired.
- `Rule` 9: `result_reads_guarded`. `RuleFamily` gains `results`. `Rule.family` gets a new arm.
  `classify` gets `.proved` for `family == .results and property == .results_checked`.
  The `Rule.fromWire(9) == null` and `NodeTag.fromWire(9) == null` lines in `proof_system.zig` tests flip.
- `Property.consumerChecked(.results_checked)` becomes true. `consumerCheckedCount()` becomes 2. The
  assertion in `proof_ratchet.zig` ("expectEqual 1") changes. The published list in
  `docs/verification.md` between the `proof-ratchet` markers moves `results_checked` from disclosed to
  consumer-checked. `scripts/check-proof-ratchet.sh` and the docs gate move in the same commit.
- `Limits.max_result_bindings: u16 = 64`. The production-limits test needs no change.
- New `ReasonCode` members (for example `result_read_unguarded`, `result_escape_present`,
  `result_binding_redefined`). `reasonAllowlist` and `runReasonProbe` in `checker.zig` need a probe
  for each, or the reason census fails.
- `schema_version` and `ir_root_domain`: no bump needed for safety. An older consumer refuses a new tag
  or rule through `fromWire` as `unknown_enum_member`, and the refusal is `recertifiable`. A bump would
  also refuse every old certificate for no gain. The self-contained binary wraps the runtime template of
  the same build, so a producer and a consumer of different versions do not meet in one artifact.
  Recommendation: no bump. If the owner wants a hard cut, bump `schema_version` to 6.
- `proof-swallow`: `checker.zig` is on the allowlist file set. The new pass uses `try` and explicit
  rejections only, and discards no error.
- Certificate bytes: the IR of the 19 Result-using files gains nodes, so `ir_root`,
  the `proof_ir` member digest, `executable_root`, and the certificate digest change for those. The
  other 80 do not move if rule 1 holds. This is the measured stop rule below.

Producer side:
- `packages/zts/src/proof_ir.zig`: lowering rules above, plus `deriveResults` as a copy of the kernel
  pass (the way `deriveTotality` is a copy), so the producer knows before emission whether the kernel
  will confirm.
- `packages/runtime/src/proof_certificate.zig`: `tagFor` and `ruleFor` arms, plus the evidence row for
  `results_checked`: `proved` with rule 9 and `node_id = entry` when `deriveResults` passes and the
  contract holds `result_safe`, else the current `tested` or `not_established` row.
- Grade cap and floor row (decided in this design, recommended). Extend the opcode cap to
  `results_checked`, as for totality. `checkEvidence` caps `grades[totality_slot]` by every trusted
  edge, and `trustedEdges` always appends the `.opcode` edge. The same IR-to-bytecode gap lies under
  results, so the achievable grade is `trusted`, the weakest on the ladder. A `proved` results edge
  without the cap would say more for results than for totality on the same trust basis, and the ratchet
  documents would overstate it. Consequences: `trusted` (index 4) does not pass the present `.tested`
  (index 3) floor row, so phase 1 moves the `results_checked` row from `.tested` to `.trusted` in
  `production_requirements`. The forcing mechanism is then the `fabricated_property` refusal, exactly as
  for totality, and not the floor. `not_established` is still refused as `required_property_not_established`.
  `countDisclosedEdges` adds `trusted.len()` only under `requires(.response_total)`; it needs the same
  term under `requires(.results_checked)`, or the disclosed count undercounts.
- Phases. Phase 1: the kernel runs `checkResults` only for a claimed `proved` results edge, and the
  producer emits that edge only when `deriveResults` passes (else the current `tested` row). Phase 2:
  the kernel runs `checkResults` on every non-refused `results_checked` claim, including `tested`, and
  refuses a mismatch as `fabricated_property`. Phase 2 turns a handler that the verifier accepts and the
  kernel cannot derive into a refused artifact. That is a user visible change (Decision 14).
- Hook point. In `checkEvidenceEntry` the `.proved => |rule|` arm calls `self.ruleAt(node)`, which is
  totality only, so a results edge would fail `rule_premise_unmet`. The arm dispatches on
  `rule.family()`: `.totality` keeps `ruleAt`, and `.results` consults the `checkResults` verdict that the
  session computed once.

What C refuses rather than accepts: rebinding (including `let r = f(); r = g()`), any alias, call
argument, return, object or array member, or closure capture of a Result; a read in a nested function
that no guard in that function dominates; a read after a guard whose negated then-arm does not always
return; a positive guard followed by a read after the `if`; more than 64 Results; a read of a binding
with no definition. The verifier accepts a positive guard with an else arm and the same forms, so C
adds refusals only where the verifier itself is unsound or where the single-definition rule bites.

Option A versus C. A accepts reassigned Results and needs a bottom-up pass with 1 MiB of scratch or a
depth stack. C needs neither and fits the corpus. If a later handler needs a reassigned Result, upgrade C
to A: the tags stay, and `result_escape` for assignment becomes `result_kill`.

## 4. Mutants the kernel must reject

Certificates are built by hand in `checker.zig` tests (see the `encodeBoundTestParts` style with a raw
`[_]IrNode{...}` array). Each of these is a fixture that the kernel must reject with a named
`ReasonCode`, and each needs a passing sibling fixture so the rejection is not vacuous.

1. A `result_read` with no guard anywhere. Expect `result_read_unguarded`.
2. A guard on ordinal 1 and a read of ordinal 2.
3. A guard in the then arm only, and the read after the `if` in the enclosing sequence.
4. `result_guard_err` whose then arm is not total (the arm is a `plain` leaf), read after the `if`.
5. A `result_escape` node present (alias, call argument, assignment), with a guarded read beside it.
6. A second `result_def` of the same ordinal (reassignment after the check).
7. A guard and a read separated by a nested `function` node (closure boundary).
8. A guard inside a `loop_node` body and the read after the loop.
9. The ok-polarity guard with the read in the else arm, and the err-polarity guard with the read in the
   then arm (polarity swap).
10. A guard node whose parent is not a two-child `sequence`, or whose next sibling is not a `branch`.
11. An aux at or above `max_result_bindings`.
12. A `proved` results edge whose certificate holds a failing pass: `fabricated_property`,
    `recertifiable = false`.
13. Honest-producer control: the corpus shape `const r = f(); if (!r.ok) { return } ... r.value`
    must be accepted, with grade `proved`.

Source-text mutants for the existing runner (`packages/tools/src/proof_checker_mutants.zig` reads
`packages/tools/src/proof_checker_mutants.zon`; rows are `{ id, file, old, new, equivalent }` and
`zig build test-proof-checker-mutants` runs them against the kernel suite). New rows, one per kernel
condition, each proposed with a fixture above that must kill it:
- polarity test removed (kills fixture 9);
- binding-ordinal equality removed (fixture 2);
- then-arm-total requirement removed for the negated shape (fixture 4);
- `function` boundary stop removed (fixture 7);
- escape refusal removed (fixture 5);
- duplicate-definition refusal removed (fixture 6);
- parent-is-sequence check on the guard removed (fixture 10);
- the `max_result_bindings` bound removed (fixture 11);
- `fabricated_property` branch for results removed (fixture 12);
- the early-return earlier-sibling scan changed to include the current child (a read in the guarded
  branch itself) or the arm index swapped (fixture 9).

`minimum_test_count` in `proof_checker_mutants.zig` is 195 today. It must rise by the number of new
kernel tests in the same commit, or a deleted test would pass unnoticed.

## 6. The interprocedural false proof

Observed: `r0/w3b_hoist3.ts` (and my `p_helper.ts`) proves `results_safe` when a Result is passed to a
helper typed `unknown` and the helper reads `.value`. The verifier never sees the read as a Result read,
because the helper's parameter is not a tracked binding.

Would the kernel catch it? A dataflow alone (Option A without the escape tag) would not, for the same
reason: the read's binding has no definition, so there is no read event to check. Option C catches it
through `result_escape`. The call `reader(late)` references the tracked binding `late` in an
argument position that no catalog row declares a safe consumer, so the lowering emits `result_escape`
and the kernel refuses to establish `results_checked`. The same escape covers `p_alias`, `p_obj`, and
a captured closure reference. `p_chain` is covered by rule 4. `p_sibling` is covered because the
lowering and the kernel pass run over every `function` node of the program, not only the handler.
`p_eqvar` is covered because the lowering emits a guard node only for the two exact forms, so the
`strict_eq` against a variable gives no guard, and the read is unguarded.

Should the kernel refuse any Result that escapes into a call? Yes, unless a catalog row declares the
callee a safe Result consumer. Default deny is the only form that does not depend on listing the ways
a Result can leak, and the listing approach is the one that failed in the verifier. The cost is that a
helper taking a Result stops proving `results_checked`. Today such a helper reads the value unchecked
in the cases that matter, so the refusal is the correct result, and the author can pass `b.value`
after a guard instead.

The verifier should refuse the same shapes. Otherwise `results_safe` stays true in the contract while the
certificate cannot prove it, and the two disagree on seven shapes (the table in section 2).

## Decisions

Decision 13, kernel rule shape for `results_checked` (C2 design). Options:
(a) Structural dominance with single definition and default-deny escape (Option C). Recommended. About
1400 lines, no new scratch, refuses reassigned Results.
(b) Must-dataflow with kill and loop support (Option A). About 1550 lines and 1 MiB more scratch. Choose
it only if the corpus gains reassigned Results.
(c) Per-read witness section (Option B). Not recommended: it adds a section and still needs the escape
and closure rules.
Approval of (a) authorizes C2 to add tags 9 to 13, rule 9, the new family, and the kernel pass, to extend the
opcode grade cap to `results_checked`, to move the `results_checked` floor row from `.tested` to `.trusted`,
and to flip `consumerChecked(.results_checked)` with the ratchet markers. It does not authorize phase 2
(kernel check of every non-refused claim).

Decision 14, the producer false proofs (seven shapes in section 2). Options:
(a) Fix them in this release. The verifier gets the same default-deny escape rule, and phase 2 (kernel check
of every non-refused claim) follows the parity gate. Behavior change: a handler that passes a Result to a
helper, aliases it, or reads it in a sibling helper stops building under `-Dverify`. Recommended, because the kernel makes
each of them a visible refusal either way and a build that accepts them states a false proof.
(b) Fix only the verifier, and stay in phase 1. The kernel checks the edge where the producer claims `proved`,
and the others stay `tested`. No new build refusal.
(c) Disclose only, in `docs/verification.md` "What is not checked, said out loud".

The owner answers: Decision 13 (a, b, or c) and Decision 14 (a, b, or c).
