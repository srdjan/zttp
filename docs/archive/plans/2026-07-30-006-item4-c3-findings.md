# Item 4 C3: the double-run does not exist

**Status:** the measurable half is done. The orchestration move is not, and needs a decision
rather than execution, for the reason below.

**Source:** the third clause of wave 4 item 4: "Move `precompile.zig`'s orchestration into
`pipeline.zig` so `PathGenerator` and `FlowChecker` run exactly once per compile." Planned as
C3 in `docs/plans/2026-07-30-003-item4-design.md`.

**Ground truth:** measured at commit `928f5771` on 2026-07-30.

## 1. The premise is false: both already run once

The clause's stated goal is that these two passes "run exactly once per compile". They already
do. Measured by temporarily counting `init` calls and driving a real analysis:

```
zts check examples/handler/handler.ts        PathGenerator.init=1  FlowChecker.init=1
zts check <fixture> --json --contract        PathGenerator.init=1  FlowChecker.init=1
```

The instrumentation was removed after measuring; it is in this document, not in the tree.

**`PathGenerator`.** The reset plan cites two sites in `compileHandler`
(`precompile.zig:1772` and `:1986`) as "up to twice per compile". They are mutually exclusive.
`:1772` sits inside `if (error_count > 0)`, the verification-failure branch, and that branch
ends with `return .{` at `:1801`. So when the first runs, the second is unreachable; when the
second runs, the first did not. The plan counted two call SITES, not two executions. Two more
sites exist (`:956` in `analyzeHandlerPaths`, `:1478` in `runGenTests`) but those are separate
entry points, one per invocation.

**`FlowChecker`.** `buildContractWithPolicy` (`:2435`) already has the reuse mechanism:

```zig
const flow_errors: u32 = if (precomputed_flow) |_| 0 else blk: {
    owned_flow = zts.FlowChecker.init(allocator, ir_view, atoms);
    break :blk try owned_flow.?.check(hf);
};
```

with a comment stating the upstream caller runs it when it can. That is not a double-run; it
is the fix for one, already in place.

This is the second item this session whose premise did not survive measurement. Wave 3 item 1
was the first, and the lesson repeats: a reviewer counting call sites in a 4,594-line file
reasonably reads two sites as two runs.

## 2. What was still real, and is now done

The design's C3 also said "bring the remaining index builders under one owner". Part of that
was free and landed:

`ContractBuilder.build` constructed the effect analyzer eleven lines BEFORE calling
`buildFacts`, so the analyzer built a private index identical to the one about to be built
beside it. The index depends only on the IR, the atom table, and the registry, so it does not
care that effects has not run. Building it first and injecting the borrow removes one index
build per contract extraction.

Verified: four contract goldens byte-identical, `verify.sh` exit 0, `zig fmt --check` clean,
`bench-check` geomean 0.99554 at 0.45 percent.

## 3. What is left, and why it is a decision

Two index builders remain private: `PathGenerator` at its four construction sites, and
`ContractBuilder`'s own index, which `pipeline.zig`'s contract paths could pass in. Wiring
those is mechanical and gated by the goldens.

The orchestration move itself is a different matter. Its stated justification was the
double-run, and that justification is gone. What remains is architectural, and real:
`pipeline.zig`'s own header says "A fourth `LoweredModule` phase is intentionally not added
until `precompile.zig`'s codegen-bearing orchestrator migrates", so the file is written in
anticipation of this move.

But it is now a large refactor with no measured performance or correctness benefit, touching
pass ordering that `pipeline.zig` documents as invariant ("type-check before flow-check",
"resolve before check"), across a 4,594-line file and an 886-line one. Doing it silently under
a premise that measurement just refuted would be the wrong call. It should be planned on its
own terms, with its own justification stated honestly as "one orchestrator instead of two, so
`LoweredModule` becomes possible", and its own risk section.

## 4. Recommendation

Wire the two remaining index builders, which is small and gated. Treat the orchestration move
as a separate item with an architectural justification, not as the tail of item 4. Record in
the reset plan that the double-run it cites does not exist, so the next reader does not
rediscover this.
