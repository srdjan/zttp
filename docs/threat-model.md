# Threat Model

This document records the public security boundaries for the current runtime
and tooling. It is intentionally narrow: only behavior implemented in this
repository is in scope.

## Assets

- Handler source, compiled bytecode, contracts, generated policies, and proof
  receipts.
- Request data crossing the HTTP boundary: method, path, headers, query, and
  body.
- Runtime capabilities exposed through `zttp:*` modules: env, outbound HTTP,
  cache namespaces, SQLite queries, filesystem-backed durable state,
  clock/random/stderr, and runtime callbacks.
- Local credentials used by hosted deploy commands when those commands are
  enabled.

## Trust Boundaries

- HTTP input is untrusted. The server enforces request body limits, header
  parsing limits, duplicate `Content-Length` rejection, chunked-transfer
  decoding checks, and static-file path checks before handler execution.
- Handler code is untrusted application code. Each request acquires an isolated
  runtime from the pool; request-local arena state is reset before reuse, and
  debug/runtime-safety builds audit arena escapes.
- Virtual modules are privileged Zig code. SDK-style modules receive an opaque
  handle and must use declared helper capabilities. Engine-coupled modules are
  part of the trusted computing base and require code review when their
  capability surface changes.
- Generated bytecode and appended payloads are integrity-sensitive. CRC checks
  catch corruption; proof receipts and JWS verification are the cryptographic
  boundary. The commitment covers the whole executable graph, not the entry
  module alone: dependency bytecode, every nested function, every constant pool,
  the module and native-module identities, the contract, the runtime policy, and
  the source profiles all move the root.
- The compiler is a producer, and its verdicts are claims. A deployed artifact
  carries a proof certificate, and an independent kernel in
  `packages/proof-checker` reconstructs the obligations from the artifact and
  checks the evidence before the process serves. That kernel is the acceptance
  boundary: it is a leaf package with no I/O, no allocator, and no dependency on
  the compiler or the server, so the authority surface an auditor has to read is
  one directory. What it does not re-derive is published in
  `docs/verification.md` and pinned by `scripts/check-proof-ratchet.sh`.
- Developer tools can read and write the local workspace. They are not a
  sandbox boundary; use normal source-control review for generated changes.

## Explicit Non-Goals

- Proof acceptance does not establish functional correctness, termination,
  availability, constant-time behavior, or side-channel freedom. It establishes
  the static safety properties the certificate names, at the grades it
  discloses, over the exact bytes that will run.
- A valid signature is not a safety claim. Provenance says who signed; it never
  raises a semantic state, and an unsigned artifact whose certificate is
  accepted is accepted.
- TLS termination is out of scope for the in-process runtime.
- The hosted control plane is out of scope for this repository.
- Third-party extensions are out of scope unless the vulnerability is in the
  SDK or module-loading boundary.
- Wasm policy runtime experiments are outside the current enforcement path.
  Current policy enforcement is in-process and fail-closed when a Wasm checker
  is requested.

## Security Invariants

- Default request logs must not include request bodies, raw header values,
  secret values, or credentials.
- Response headers reject CR, LF, and NUL before reaching the wire.
- Static files must stay within the configured root after canonical path
  resolution and must not follow symlink escapes.
- Runtime policy denies must emit security events.
- Dev-mode execution is not treated as sandboxed; precompiled and deploy paths
  are the sandboxed surfaces.
- Only bytecode that passes `packages/zts/src/bytecode_verifier.zig`
  (opcode legality, operand bounds, constant pool, stack discipline, jump
  targets) is dispatched into the VM. Rejected bytecode is dropped before
  any VM state is allocated.
- A configured capability policy that cannot be read, parsed, or applied stops
  the command. No analyzer boundary substitutes an unrestricted policy and then
  publishes a verdict, a contract, an artifact, or a proof capsule.
- A proof bundle is untrusted input. `zttp proofs verify` accepts only the
  `contract`, `binary`, and `replay` components, requires a `contract`, and
  requires each component to carry a distinct relative path and a lowercase
  sha256. Every path segment is opened without following symlinks, so a
  component that resolves outside the bundle directory is refused rather than
  hashed.

## Known Footguns

- `multipart/form-data` request bodies cross the HTTP boundary as raw bytes.
  The runtime enforces `Content-Length` and total body size (default 1 MiB).
  Use `decodeFormMultipart` from `zttp:decode` or handler-owned parsing, and
  treat multipart boundaries and quoted-string handling as untrusted input.
