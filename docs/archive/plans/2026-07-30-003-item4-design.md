# Wave 4 Item 4 Design: one import index, one orchestrator

**Status:** approved scope, planned into three plans.

**Source:** wave 4 item 4 of `docs/plans/2026-07-28-001-reset-simplification-plan.md`: "Add the
shared import and binding index computed once after parse, and the shared IR shape helper
library. Move `precompile.zig`'s orchestration into `pipeline.zig` so `PathGenerator` and
`FlowChecker` run exactly once per compile."

**Ground truth:** measured at commit `82369b67` on 2026-07-30.

## 1. Scope

| Plan | Clause |
| --- | --- |
| C1 | Extend `ModuleFacts` with a complete per-import record and migrate all six analyzers onto it, each keeping its own filter. The index is injected, so an analyzer with no injected index still builds its own. |
| C2 | `pipeline.zig` owns one `ModuleFacts` per compile and injects it into the four passes it constructs. |
| C3 | Move `precompile.zig`'s orchestration into `pipeline.zig` so `PathGenerator` and `FlowChecker` run exactly once, and inject the index into the passes precompile owns. |

**The shared IR shape helper library is deferred.** It is the vaguest clause in the item: the
reset plan defines it only as "a shared read-only IR shape helper library", it changes no
behavior, and it would touch all six analyzer files a second time. Which shapes actually
repeat is far clearer after C1 has rewritten the one traversal they demonstrably share. This
is a decision to sequence, not to drop.

## 2. Two facts that block the obvious approach

### 2.1 `ModuleFacts` is not a superset of what the six need

B2 built the index for `ContractBuilder`. Two gaps make it unusable as-is by the others:

- `generic_bindings` is populated only when a function has contract extractions OR contract
  flags (`module_facts.zig`, the `has_extractions or has_flags` guard). `sha256` has neither,
  so it has no entry. But `path_generator`, `flow_checker`, and `bool_checker` need a
  slot-keyed record for EVERY builtin import.
- `ModuleFacts` records only builtin-or-partner-registered modules. `strict_checker` and
  `effect_inference` record every import, including modules that are neither.

So C1 adds a new collection rather than reusing `generic_bindings`. The existing four
collections are not touched, because `ContractBuilder` still reads them and the four contract
goldens still pin their effect.

### 2.2 "Computed once" needs an owner, and that owner is what C3 creates

The index cannot be computed once until something owns it for the duration of a compile.
`pipeline.zig` already constructs four of the six, so it is the natural owner for those. The
other two are constructed inside `precompile.zig`, which is exactly the orchestration C3
moves. Hence the ordering: C1 makes the index sufficient and the analyzers able to accept it,
C2 gives four of them one instance, C3 brings the remaining two under the same owner.

C1 alone therefore removes the duplicated CODE without removing the duplicated WORK. That is
deliberate: it is the step whose equivalence can be proven per analyzer, before any
orchestration moves.

extension bindings compiled in at build time.

## 4. The design

`ModuleFacts` gains one collection:

```zig
/// Every import specifier in the module, in node order then specifier order,
/// with no filtering at all. This is what the analyzers read; each applies its
/// own filter at read time so its behavior is unchanged.
pub const ImportRecord = struct {
    slot: u16,
    module_specifier: []const u8,
    imported_name: []const u8,
    resolution: enum { builtin, partner, unresolved },
};

imports: std.ArrayList(ImportRecord) = .empty,
```

Three properties make this safe:

- **Additive.** The four existing collections keep their current construction and content, so
  `ContractBuilder`'s output cannot move and the four contract goldens stay byte-identical.
- **Unfiltered.** Because it records `unresolved` imports too, it is a superset of every
  analyzer's need. Each analyzer filters at read time, preserving its own behavior exactly. No
  analyzer's filter is "corrected" in C1 even where two of them disagree.
- **Injected, not assumed.** Every analyzer's `init` gains an optional
  `facts: ?*const ModuleFacts`. Null means build a private one, which is what the in-file
  tests will keep doing. So C1 needs no orchestration change and no test rewrite except where
  a test asserts on the scan directly.

Lifetime: `ImportRecord` strings are owned by the facts, so the facts must outlive every
analyzer reading them. That is already the rule for the borrowed extraction rules B2
documented, and C2/C3 make it structural by giving the index the same scope as the compile.

## 5. Behavior preservation is the whole gate

Nothing in item 4 is supposed to change a single diagnostic. The gate for each plan is
therefore differential, in the shape B1 established and B2 reused:

- Keep the old `scanImports` alive under a private name, run both, and assert the derived
  state is identical over a corpus, before deleting either.
- For the two analyzers whose filters disagree with the others, assert the disagreement
  SURVIVES. A migration that accidentally unifies the filters is a behavior change disguised
  as a cleanup.
- The four contract goldens must stay byte-identical throughout, because
  `effect_inference` feeds `contract_builder`.
- `zig build test` must collect the same or more tests, never fewer. Wave 3 item 1 is the
  cautionary precedent: an import that looked like coverage and provided none.

## 6. Risks

**The differential state is not a flat value.** Four of the six derive hash maps, not lists,
so "identical" means same key set and same value per key, not a memcmp. Each plan's harness
has to iterate and report the diverging key, or a failure will say only "maps differ". B1's
first harness had exactly this defect and had to be rewritten mid-plan.

**`precompile.zig` is 4,594 lines and `pipeline.zig` is 886.** C3 moves orchestration between
them. This is the one clause that can change WHEN a pass runs, not just where it is
constructed, and pass ordering carries real invariants that `pipeline.zig`'s header documents
("type-check before flow-check", "resolve before check"). C3 gets its own risk section in its
own plan, and it does not start until C1 and C2 are green.

**Double construction is not obviously redundant.** `HandlerVerifier` and `FlowChecker` are
each constructed in both `pipeline.zig` and `precompile.zig`. Before removing either, C3 must
establish that the two constructions receive equivalent inputs. They may not: the reset plan
notes `FlowChecker` is constructed a second time "when not precomputed", which suggests a
conditional the move has to preserve.

## 7. Out of scope

- The shared IR shape helper library. Deferred, see section 1.
- Changing any diagnostic, any filter, or any pass ordering.
- Any change to the four existing `ModuleFacts` collections.
- Unifying the six analyzers' differing filters, even where the difference looks accidental.
  If one is wrong, that is a separate finding with its own fix and its own evidence.
