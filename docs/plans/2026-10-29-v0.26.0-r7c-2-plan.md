# v0.26.0 R7c-2 pi tools on the production check - Plan

## Goal Capsule

- **Objective:** A model that calls `pi_repair_plan`, `pi_goal_check`, or `zts_expert_narrow` gets the verifier and flow findings that `zts check` reports for the same file. A ZTS309 refusal then gets a diagnostic and a repair plan, and the W re-record captures the production analysis.
- **Means:** each tool runs one production check with the R7c-1 observer and builds its envelope from the observed view (KTD1).
- **Authority:** this plan, then the R7c design (`docs/plans/2026-10-29-v0.26.0-r7c-design.md`), then the v0.26.0 plan (`docs/plans/2026-10-27-v0.26.0-plan.md`). Decision 46(a) is decided and governs R6 and R7.
- **Stop conditions:** any difference in the census test (U3) stops the work and goes to the owner. A pin moves outside the known W set: stop and report. The implementer reaches the turn budget: stop and hand back status and open items.
- **Execution profile:** Sonnet implements U1 to U3 in order with a total turn budget of 40. Opus reviews the diff line by line and runs the gates itself.
- **Who finishes:** commits land on local `main`. The owner pushes.

## Product Contract

### Summary

The three pi tools stop running bare single-file checkers. Each tool runs the production check once, reads the typed verifier and flow diagnostics through the observer that R7c-1 added, and writes its envelope from them. A check that stops before the verifier returns the production diagnostics, per Decision 46(a). A committed census test over `tests/corpus` holds the tools equal to production.

### Problem Frame

Decision 43 requires this move before the W re-record (see origin: `docs/plans/2026-10-28-v0.26.0-a3-design.md`, section R1.5). The ZTS309 phase reads the type checker's record. `pi_repair_plan` builds `HandlerVerifier` with no type checker, so a ZTS309 refusal gets no diagnostic and no repair plan from that tool. The bare `FlowChecker` in all three tools cannot see imports. The R7c census found that the tools differ from production in 97 of 143 analyzed corpus cases (see origin).

### Requirements

**Analysis route**

- R1. Each of the three tools takes its flow witnesses, and `pi_repair_plan` also takes its verifier diagnostics and plans, from one production check through the observer. No tool constructs `HandlerVerifier` or `FlowChecker` itself.
- R2. `pi_repair_plan` analyzes the source once per call. The second analysis through `pi_goal_check.unprovenGoals` goes.
- R3. A position in tool output equals the position that `zts check --json` reports for the same diagnostic.
- R4. Tool output is byte-identical under two different workspace roots. The test "a repair plan reads the same from two different workspaces" stays green.

**Verdicts**

- R5. The `ok` verdicts keep their present meaning over the production lists. `pi_repair_plan` reports `ok: false` when there is a verifier error, a flow diagnostic for a requested goal, or an unproven requested goal. `pi_goal_check` keeps its `ok` and `unproven` fields.
- R6. When the production check stops at a parse, type, strict, or import error, the tool returns `ok: false` with the production JSON diagnostics as its diagnostics, and no witnesses or plans.
- R7. When the file passes the early stages and has no handler, the tool returns its present error "no handler function found in file".
- R8. A tool never reports `ok: true` for a call in which the observer did not run.

**Callers**

- R9. The `pi_goal_check` envelope keeps its `ok` and `witnesses` keys, which `parseGoalCheckResult` in `packages/pi/src/autoloop.zig` reads. `pi_repair_plan.planFromSource` keeps analyzing the in-memory `source` bytes, not the file on disk, for `pi_goal_candidate.zig`.

**Measurement**

- R10. A committed census test iterates every case in `tests/corpus`, asserts a floor of 182 cases, compares `pi_repair_plan` diagnostics with the production diagnostics by code and position, and fails on any difference. It reports the count of refusals before analysis.

### Key Decisions

- **Decision 46(a): a check that ends before the verifier and the flow pass returns the production result, not a bare-checker fallback.** The tool then says what `zts check` says, and a verdict never stands on an analysis that checked nothing. Options (b), a bare-checker fallback, and (c), a tool error with no diagnostics, were rejected (see origin). Governs R6, R7. Conflict call-out for the owner: the no-handler branch was chosen on the premise that `zts check` gives such a file no diagnostic. A probe on 2026-10-29 showed one ZTS500 error at 1:1 instead. This plan keeps R7 as decided, and the owner may prefer that the tool return that ZTS500.

### Scope Boundaries

- R4 row 18, H10 part 2, the changelog and `docs/verification.md` entries, the DeepSeek re-record, and X are later W items in `docs/plans/2026-10-29-v0.26.0-w-handoff.md`. They are not in this plan.
- `zts check` output does not change. R7c-1 already holds it byte-identical, and this plan does not touch the check.
- The `solveCounterexample(...) catch continue` in `pi_repair_plan.zig` moves with the witness code unchanged. Considered and not changed here: it drops a witness, not a diagnostic, and `ok` does not depend on it. A census difference in witnesses would reopen it.
- Other pi tools that already use `common.checkJsonOutcome` (`zts_check`, `pi_specs_status`) are not touched.

## Planning Contract

### Key Technical Decisions

- KTD1. **One production check per call, envelope body built inside `on_checked`.** The view borrows the IR, the atom table, and both diagnostic lists only during the callback, so the tool projects witnesses, solves counterexamples, and builds plans there (see origin, Mechanism). `repairSubjectName` and `DiagnosticProjection.projectFlowWitness` need the borrowed `ir_view` and `atoms`, which the view carries. The callback buffers the diagnostics, witnesses, and plans body, and records whether it saw a verifier error or a flow diagnostic for a requested goal. The tool writes `ok` after the check returns, because the check sets `properties` and `flow_unresolved` after the observer runs and the view does not carry them.
- KTD2. **One shared helper owns the call.** It lives in `packages/pi/src/tools/common.zig` or a new `packages/pi/src/tools/production_check.zig`. It resolves the workspace path, runs `discoverProjectPaths`, reads the policy and the SQL schema path, passes `json_mode = true` and the observer, and returns the `CheckResult`. It replaces `common.discoverEnvPublic` in the three tools, because `env_public` then comes from the policy as in production. It passes the workspace-relative path for the `file` field, as `common.checkJsonOutcome` does (R4).
- KTD3. **The callback context records that it ran, and the tool fails closed without it.** The context holds a `ran` flag, the envelope buffer, and any non-`OutOfMemory` failure from writing. The callback error set is `error{OutOfMemory}` only, because the check turns any other error into a false `compiler_io_failure` diagnostic. After the check returns, the tool decides from three states. The observer ran: emit the envelope, and report a stored failure as a tool error. The observer did not run, the check reports `has_handler == false`, and `parse_errors`, `bool_errors`, `type_errors`, and `strict_errors` are all zero: return the no-handler error (R7). The diagnostics list cannot be this discriminator, because the spec stage adds an error-severity ZTS500 at 1:1 to a file with no handler. Every other case: return `ok: false` with the production JSON diagnostics (R6). R8 follows, because no path reaches `ok: true` without `ran`. Reason: the fail-open class in AGENTS.md, where an empty list read as clean (`docs/solutions/logic-errors/empty-baseline-made-a-file-destroying-edit-prove-clean.md`).
- KTD4. **Positions use the check's own source remap.** Observer positions come from `getLoc` and are raw. For a typed source the helper maps each position with the same `normalize_positions` source view that the check applies to its JSON diagnostics in `runCheckOnlyFromSourceWithPathAllocator`. `remapDiagnosticsToSource` is private in `packages/tools/src/precompile_check_run.zig`. The same view setting appears in `packages/tools/src/precompile.zig` and `packages/tools/src/precompile_gen_tests.zig`, so the implementer reuses that public surface or exposes the smallest mapping function. A new row in `scripts/module-boundary.allow` needs a stated reason in the commit (R3).
- KTD5. **The census compares like with like.** Each `pi_repair_plan` diagnostic entry gains a `code` field: `zts.DiagnosticProjection.code(.verifier, diag.kind)` on the observer path, and the production `code` on the R6 path. When production ran the verifier (`verify_ran`), the test compares the tool's diagnostics with the production JSON diagnostics whose code `zts.DiagnosticProjection.allCodes()` lists with `source == .verifier`, because a JSON diagnostic carries no stage field. Otherwise the test compares them with all production JSON diagnostics, which R6 makes the tool's diagnostics. Each comparison is by code, line, and column. A tool error before the check, and the no-handler error of R7, count as refusals before analysis: the test reports their count and does not compare them. The census exemption in AGENTS.md permits the iteration.
- KTD7. **Admission and extension refusals go through the check.** `planFromSource` and the other two tools drop the `common.admitToolSource` gate, so an admission failure or a `.js` path reaches the production check and follows R6. The design states that Decision 46(a) gives the tool the production ZTS052 diagnostic (see origin, the struck Decision 47), and a pre-check gate would pre-empt it. After this change, the only tool errors before the check are an unknown goal and an unreadable workspace path.
- KTD8. **`zts_expert_narrow` gains a `diagnostics` key only on an early stop.** Its normal envelope stays `{"path","witnesses"}`. Under R6 it returns `{"path","diagnostics","witnesses":[]}` with the tool result marked not ok. The W re-record captures this shape.
- KTD6. **`unprovenGoals` stays public or folds into the helper.** The implementer chooses and names the choice in the commit (see origin). `autoloop.zig`, `pi_goal_candidate.zig`, and `evaluateSource` already reach the production check through it and need no change.

### Assumptions

- The design's statement that a file with no handler gets no diagnostic is wrong: the feasibility review probed three such files and each got one ZTS500 error. KTD3 uses the stage error counters instead.
- The R7c census numbers (182 cases, 39 refused before analysis, 46 equal, 97 different) were measured at `257a8482`. After KTD7 the 39 parse and admission refusals go through the check, so the refusal count that the census reports will differ from 39. R7c-1 kept `zts check` byte-identical, so the corpus behavior of production is unchanged since then. The census test measures the current state, and only the floor of 182 is asserted.
- Test 2 needs a literal witness count from production. The implementer measures it after the move and records the failing value before the move in the commit (see origin, test 2).

### Sequencing

U1 builds the helper and moves `pi_repair_plan`, because that tool exercises every part of the view. U2 moves the two flow-only tools onto the same helper. U3 adds the census test last, because it asserts equality for the finished state.

## Implementation Units

### U1. Shared helper and `pi_repair_plan` on the production check

- **Goal:** `pi_repair_plan` reads one production check through the observer, with the early-stop and no-handler behavior of Decision 46(a).
- **Requirements:** R1, R2, R3, R4, R5, R6, R7, R8, R9. KTD1, KTD2, KTD3, KTD4, KTD5, KTD6, KTD7.
- **Dependencies:** R7c-1 (`817ede95`), which is on `main`.
- **Files:** `packages/pi/src/tools/common.zig` or new `packages/pi/src/tools/production_check.zig`, `packages/pi/src/tools/pi_repair_plan.zig`, `packages/pi/src/tools/pi_goal_check.zig` (only if KTD6 folds `unprovenGoals`), `packages/pi/src/tests.zig` (only for a new helper file: add its import row, or its tests do not run under `test-expert-app`), tests in `packages/pi/src/tools/pi_repair_plan.zig`.
- **Approach:**
  1. Write the helper per KTD2 with the callback context of KTD3.
  2. In `planFromSource`, keep goal parsing. Replace `common.admitToolSource` (KTD7), the parser, the bare verifier, the bare flow checker, and the `unprovenGoals` call with one helper call.
  3. Move diagnostic, witness, and plan writing into the callback, with positions mapped per KTD4 and a `code` field on each diagnostic per KTD5.
  4. After the check returns, write `ok` per R5 from the callback's flags and the `CheckResult` properties (KTD1), as `unprovenGoals` decides the verdict today.
- **Execution note:** write tests 1, 4, and 5 for this tool first, run them, and confirm that each fails for the reason the design names.
- **Patterns to follow:** `pi_goal_check.unprovenGoals` for project discovery and policy reading. `common.checkJsonOutcome` for the absolute and relative path pair. The observer test in `packages/tools/src/precompile_check_run.zig` for the callback shape.
- **Test scenarios:**
  - Test 1: a handler with an unguarded read of a value that may be `undefined` (a ZTS309 shape from the A3 design probes) returns exactly one diagnostic whose `code` field is ZTS309, and exactly one plan. Before the move it returns neither.
  - A source at a `.js` path returns `ok: false` with one diagnostic whose `code` is ZTS052, and no witnesses or plans (KTD7). Before the move it returns a tool error.
  - Test 4: one of the 9 early-stop census cases returns `ok: false`, the production diagnostic code and position, an empty `witnesses` array, and an empty `plans` array.
  - Test 5 (this tool): a file that parses and has no handler returns the error text "pi_repair_plan: no handler function found in file".
  - The existing test "a repair plan reads the same from two different workspaces" stays green with no edit.
  - The existing `pi_repair_plan` tests for unchecked `Result.value`, unchecked optional use, and missing fallback Response keep their expected outputs, or the commit attributes each changed literal to the production analysis.
- **Verification:** tests 1, 4, and 5 failed before the change and pass after it. `test-expert-app` fails only on its two known W tests.
