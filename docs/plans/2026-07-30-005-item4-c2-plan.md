# Item 4 C2 Implementation Plan: one index per compile, threaded through the pipeline

**Status:** planned.

**Source:** section 1 of `docs/plans/2026-07-30-003-item4-design.md`. C1
(`2026-07-30-004`) is done at commit `8213f1ef`.

**Goal:** Build the import index once per compile and inject it into the four passes
`pipeline.zig` constructs, so those four stop building a private one each.

**Ground truth:** measured at commit `8213f1ef` on 2026-07-30.

## 1. Correction to the design: the pipeline cannot own the index

Section 1 of the design says "`pipeline.zig` owns one `ModuleFacts` per compile". That is not
implementable as written, and the reason is structural.

`resolve` constructs `BoolChecker` and `StrictChecker` as stack locals and then MOVES them into
the returned `ResolvedModule` (`pipeline.zig:194-206`). A `facts` pointer into a stack local, or
into a field of the `ResolvedModule` being returned, dangles the moment `resolve` returns. The
same applies to `check` and `CheckedModule`.

The file already documents this hazard and its solution. `ResolveOptions.type_env` carries the
note "The pointed-to TypeEnv must outlive the returned ResolvedModule", and the header explains
that `CheckedModule` borrows `*const ResolvedModule` precisely "because `HandlerVerifier` holds a
pointer back to the `TypeChecker` and the borrow keeps that target address stable in caller
storage".

So the index is **caller-owned and pipeline-threaded**, exactly like `type_env`. The compile
owns one; the pipeline passes a borrow into the four analyzers. That satisfies the item's real
requirement, "the shared import and binding index computed once after parse", without inventing
an ownership model the phase structs cannot support.

## 2. Design

- `ResolveOptions` gains `module_facts: ?*const ModuleFacts = null`, injected into `BoolChecker`
  and `StrictChecker`.
- `check` gains a matching parameter, injected into `HandlerVerifier` and `FlowChecker`. It takes
  an options struct rather than a fifth positional parameter, so the next addition does not
  churn every call site again.
- `pipeline.buildModuleFacts(allocator, parsed, registry)` is added as the one obvious way for a
  caller to build it, so four call sites do not each reinvent the argument order.
- Null keeps C1's behavior exactly: each analyzer builds a private index. Every existing caller
  and test therefore compiles and behaves unchanged until it opts in.

## 3. Why the gate is unusual

C1 made injection behavior-neutral by construction: an analyzer with no injected index builds an
identical private one. So C2 cannot be judged by output at all - every diagnostic, every golden,
and every test must be byte-identical, and that is necessary but proves nothing about whether
the work was actually shared.

The gate therefore has two halves:

1. **Nothing changed.** Four contract goldens byte-identical, `verify.sh` exit 0, collected test
   count not lower.
2. **The work is actually shared.** A test that injects an index and asserts each analyzer's
   `owned_facts` is null, which is directly observable and cannot pass vacuously. Without this
   half, C2 could be a no-op that looks successful - the same trap as wave 3 item 1, where an
   import that read as coverage provided none.

## 5. What must not change

- Any diagnostic. C2 is a wiring change; if output moves, it is wrong.
- The analyzers' filters or their private-index fallback. A caller that passes nothing must keep
  working, because `precompile.zig` has sites C3 has not reached yet.
- Pass ordering, and which orchestrator constructs what. Moving construction is C3.
