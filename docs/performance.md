# Performance

Current public performance claims and runtime knobs are listed here. Benchmark
history belongs in the benchmark repository or changelog, not in maintained
docs.

## Public Numbers

Measured on Apple M4 Pro with ReleaseFast builds:

| Metric | Current claim |
|---|---:|
| Cold-start floor | about 3.5 ms |
| Typical cold start | about 7-15 ms, host-load dependent |
| Baseline RSS after first response | about 13 MB |
| HTTP throughput on trivial JSON handler | about 112k req/s |
| Deployed local binary | about 4.8 MB |

Cold start is measured from process launch to first complete HTTP response for
`zttp serve -e <handler>`. Treat it as a distribution: scheduling jitter and
host load move the tail.

Run the in-repo benchmark suite with:

```bash
zig build bench
zig build bench-check
```

These commands cover the in-process benchmark suite and advisory threshold
check. The public cold-start, RSS, and HTTP-throughput numbers above are pending
receipt-backed measurement in this repo; until that lands, treat them as
historical/manual benchmark evidence rather than output mechanically reproduced
by `zig build bench`.

For release readiness, treat `zig build bench-check` as an advisory confidence
gate. If one benchmark misses the threshold once, rerun immediately on the same
machine; a clean rerun clears the release, while two consecutive failures block
for investigation.

To replace the checked-in baseline after an intentional performance change,
commit the source and run:

```bash
zig build bench-record
```

The command refuses a dirty or uncommitted tree. It atomically records the
per-benchmark best result from five runs together with the source commit, Zig
version, host details, run count, and aggregation method. Review and commit the
resulting `benchmarks/perf-baseline.json` separately from the tooling change.

## Compiler Measurements

Use Zig 0.17.0 and ReleaseFast for compiler measurements:

```bash
zig build compile-bench -Doptimize=fast -- --json --iterations 50
zig build compile-bench -Doptimize=fast -- --json --iterations 50 --profile check
```

The default profile measures typed parsing and code generation. The `check`
profile measures typed parsing, type and strict checks, handler verification,
and flow analysis. It reports diagnostic counts; completing a benchmark does
not mean its handler is proven. Neither profile includes filesystem import
loading or artifact acceptance.

Both profiles report phase timings, teardown, successful allocation calls,
cumulative allocation bytes, and peak live allocator bytes shared across all
phases. Peak allocator bytes are requested storage, not RSS. Fixture generation
is outside the measurement. The corpus includes small handlers and generated
cases for dense expressions, wide lists, nested functions, typed declarations,
escaped strings, constant expressions, and a 4 MB string literal.

IR source locations retain line and column alongside byte spans: codegen needs
them for every emitted node. Capacity estimates remain bounded so a large
literal does not reserve nodes in proportion to its byte length.

Code generation folds complete constant expression trees without rewriting the
IR used by type checking, flow analysis, or proof lowering. Evaluation is bounded
to 64 visited nodes per attempt and allocates no replacement map. Integer
division produces a float, remainder follows the VM's sign convention, and
overflow and non-finite arithmetic remain runtime operations. Short-circuit
expressions fold only when both operands are constant, preserving calls and
their proof witnesses.

The runtime parser wrapper and `DirectCheckSource` borrow unescaped string
literals from the immutable source they already retain. Codegen copies runtime
strings before parser teardown. The general parser and `ConstantPool.init`
keep owning copies; opting in with `borrowSourceStrings` or
`ConstantPool.initBorrowingSource` requires the source to outlive the parser
and its constant pool. Decoded escape buffers remain owned by the pool.

Measured on 2026-10-22 with Zig 0.16.0 ReleaseFast on an Apple M4 Pro,
macOS 26.6.2, against compiler commit `6f8aef6a`. Both binaries used the same
extended harness. These are medians of five paired runs, with 100 iterations
per compile fixture and 20 per check fixture; fixture source storage is excluded.

| Fixture and profile | Before | After |
|---|---:|---:|
| Constant expressions, compile time | 476 µs | 391 µs |
| 4 MB literal, compile peak allocator bytes | 9,106,232 | 4,911,928 |
| 4 MB literal, check peak allocator bytes | 5,035,950 | 841,646 |

The constant-heavy case compiles 17.9% faster. Other compile fixtures range
from 4.0% faster to 2.3% slower; the dense nonconstant case pays the largest
folding overhead. Check timings range from 1.8% faster to 0.7% slower.
A separate five-pair experiment with keyword comparisons generated by string
length regressed several small fixtures by 1.5–4.2%, with only small gains
elsewhere. The existing `StaticStringMap` keyword lookup is retained.

## What Affects Latency

- Build-time precompile with `zig build -Dhandler=handler.ts` or `zttp build`
  embeds handler bytecode and removes parse/codegen work from startup.
- `-n` controls isolated runtime count. The default is derived from CPU count
  and clamped to 8-128.
- `-m` sets a per-runtime allocator ceiling. The default is no explicit limit.
- `zttp:fetch` depends on external systems and outbound HTTP runtime flags.
- The response cache is gated by certificate-accepted `deterministic` and
  `read_only` properties plus a contract with no request-header or body
  dependency. The shipped production policy accepts neither property, so this
  cache remains off today. A contract claim by itself never enables it.

## Engine Optimizations

The current runtime includes:

- hidden-class shapes for request, response, and object literals;
- polymorphic inline caches for property access;
- binary search for larger object property tables;
- lazy string hashing and pre-interned HTTP atoms;
- specialized bytecode for type-directed boolean and comparison paths;
- request-scoped allocation with bulk reset.

These details are implementation notes, not public API. Use the benchmark
commands above when changing engine or runtime hot paths.

## Deployment Notes

`zttp deploy` produces a local self-contained binary under
`.zttp/deploy/<project-name>`. Run multiple instances behind a reverse proxy
or platform load balancer for higher throughput. A standalone `zttp serve`
process should not be exposed directly without the usual network controls.

For current limits and failure behavior, see [Reliability](reliability.md).
