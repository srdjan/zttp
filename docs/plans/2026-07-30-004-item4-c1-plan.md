# Item 4 C1 Implementation Plan: one import scan, six readers

**Status:** in progress. Tasks 1-4 done (index, effect_inference, strict_checker, bool_checker).

**Source:** section 4 of `docs/plans/2026-07-30-003-item4-design.md`.

**Goal:** Replace six independent `scanImports` implementations with one read over an extended
`ModuleFacts`, changing no diagnostic and no filter.

**Ground truth:** measured at commit `3ddbbfdf` on 2026-07-30.

## 1. Shape of the work

One task to extend the index, then one task per analyzer, in increasing order of risk. The
order is chosen so the pattern is validated on the simplest projection before it reaches the
one with three collections.

| # | Analyzer | Why this position |
| --- | --- | --- |
| 2 | `effect_inference` | Simplest projection, `HashMap(slot, {module, name})`, no filter. Validates the pattern. Also the highest-value early check, because it feeds `contract_builder` and therefore the four contract goldens. |
| 3 | `strict_checker` | Same no-filter read, into a list instead of a map. |
| 4 | `bool_checker` | 113 in-file tests, the best evidence of the six. First one with the builtin filter. |
| 5 | `path_generator` | Builtin filter, one map, but four construction sites in `precompile.zig`. |
| 6 | `flow_checker` | Three derived collections plus a special-cased `env_fn_slot`. |
| 7 | `handler_verifier` | The odd filter: it pre-screens whole modules for having any result or optional export, then filters functions again. Two levels, and the only one that iterates `builtin_modules.all` directly. |

## 2. Task 1: extend `ModuleFacts` and build the shared corpus

**Goal:** a complete, unfiltered per-import record, plus the corpus every later task's
differential test runs over.

Add to `packages/zts/src/module_facts.zig`:

```zig
pub const ImportRecord = struct {
    slot: u16,
    module_specifier: []const u8,
    imported_name: []const u8,
    resolution: enum { builtin, partner, unresolved },
};
```

populated in the existing walk, before the builtin-or-partner filter that currently `continue`s
past unresolved modules. That is the one structural change to `build`: the filter stops being
an early `continue` for the whole import and becomes a branch that still records the specifier.
The four existing collections must observe the identical filter they do now.

Add `packages/zts/src/tests/import_corpus.zig` holding the sources every differential test
uses, so six tasks share one corpus rather than inventing six:

- a single builtin import
- several names from one module
- the same module imported twice
- the same name imported twice
- an aliased import (`import { env as e }`), which separates `imported_atom` from
  `local_binding.slot`
- a module that is neither builtin nor registered
- a builtin and an unresolved module in one file
- a function with no extractions and no flags (`sha256`), which has no `generic_bindings`
  entry and is exactly the case section 2.1 of the design says the six need
- no imports at all

**Verify:** `zig build test-contract-golden` exits 0 with all four goldens byte-identical,
which proves the filter change did not leak into `ContractBuilder`. New unit tests assert the
`imports` collection against each corpus entry, including that an unresolved module IS recorded
and that it does NOT appear in `modules` or `functions`. Allocation-failure ladder still green.

**Commit:** `feat(contract): record every import in the index, unfiltered`.

## 3. Tasks 2 to 7: one analyzer each

Every task has the same four steps, and the first three land before anything is deleted.

1. Add `facts: ?*const ModuleFacts` to the analyzer's `init`. Null keeps today's behavior by
   building a private index internally, so no existing caller or test changes.
2. Add the replacement scan that reads `facts.imports` and applies THIS analyzer's filter,
   under a private name, next to the original.
3. Add a differential test over the shared corpus asserting the two derived states are
   identical. For a hash map that means same key set and same value per key, reported per
   diverging key: a harness that says only "maps differ" is not good enough, which B1 learned
   the hard way when `expectEqual` on a struct reported "expected false, found true".
4. Delete the original scan and the duplicated traversal.

**Filter preservation is asserted, not assumed.** `strict_checker` and `effect_inference`
record unresolved imports; the other four do not. Each task's differential test must include
the corpus entry with an unresolved module and assert the analyzer's own answer, so a
migration that accidentally unifies the filters fails rather than silently widens analysis.

**Verify, per task:** the analyzer's own in-file tests green; the differential test green; `zig
build test-zts` green; the four contract goldens byte-identical; `zig build test` collects no
fewer tests than before.

**Commit, per task:** `refactor(<analyzer>): read imports from the shared index`.

## 4. What must not change

- Any diagnostic, from any of the six.
- Any of the six filters, including the two that disagree with the other four.
- The four existing `ModuleFacts` collections, in construction or content.
- Pass ordering, and which orchestrator constructs what. That is C2 and C3.
- The number of times each analyzer runs per compile. C1 removes duplicated code only; the
  duplicated WORK is C2 and C3, and saying otherwise would overstate what this plan delivers.

## 5. Findings

To be filled in during execution.

| # | Finding | Direction | Resolution |
| --- | --- | --- | --- |
| 1 | Two atom-name resolvers disagreed when there is no atom table. `bool_checker.resolveAtomName` has a documented fallback (without a table, string constants take priority over predefined atoms, because import specifiers go through `addString`); `ModuleFacts` had only the with-table path and so resolved no names at all. `checkSourceFull` builds a checker with `null` atoms, so nine sound-mode tests failed | would have silently emptied bool_checker's type map on the no-table path | Fallback copied verbatim into `ModuleFacts` so the two cannot drift, and pinned by its own test so it cannot be deleted as dead code. Note this also changes the no-table path for `contract_builder`, which previously indexed nothing there; the goldens are unaffected because precompile always passes a table |
| 2 | The corpus differential could not have caught finding 1: every corpus case passes a real atom table. The 113 pre-existing `bool_checker` tests are what caught it | the differential read as stronger evidence than it was | Every differential now runs each corpus case in BOTH atom modes, and the remaining three migrations do so from the start. This is the same lesson as wave 3 item 1: a check that reads as covering more than it does |
| 3 | Two of my own filtered test runs were vacuous. `zig build test-zts -- --test-filter "a\|b"` passes a literal `a\|b` to Zig, not a grep alternation, so it matched zero tests and exited 0 | a test run that passed for the wrong reason, twice | The full `zig build test-zts` run after each migration is the real evidence, and both were green. Recorded because it is the second time this session a verification step silently did nothing; the first was `cp -i` prompting |
| 4 | The legacy builtin filter `builtin_modules.fromSpecifier(module) == null` translates to `resolution == .builtin` ONLY, not `!= .unresolved`. `fromSpecifier` searches `builtin_modules.all` and never consults a manifest registry, so a partner-registered module was skipped before and must stay skipped | would have widened three analyzers to partner modules | `.partner` is excluded alongside `.unresolved` in `bool_checker`, and the same rule applies to `path_generator`, `flow_checker`, and `handler_verifier` |
